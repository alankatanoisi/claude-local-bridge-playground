1. Yes—but there are three different kinds of “peek”

Our host can inspect the conversation it retains and the request it builds. The model already has optional tools for recalling its own conversation history. But the model does not currently have a dedicated tool for inspecting the complete outbound context snapshot, and its ordinary file tools cannot open ~/.bridge-runner.

The tilde in ~/.bridge-runner means your home folder; on this Mac that is /Users/alanman/.bridge-runner. That directory holds several different kinds of records. It is not a single live “brain dump.”

Who is looking? What is available today? Important limit
The local host program The live message array, system instructions, tool definitions, projection decisions, request objects, and returned usage. This is program data, not access to the model’s internals.
The model working inside the runner The request supplied to it, plus optional search_history and expand_history calls. History tools retrieve retained conversation entries, not the complete request envelope or arbitrary log files.
You or an authorized external diagnostic session Saved traces, session checkpoints, transcripts, event ledgers, and archives. Capture level, timing, redaction, and missing records limit reconstruction.

“It was logged” and “the model can see it” are separate facts. A host write to disk does not insert that file into the next model request. To make a record visible to the model, something must explicitly place its contents or a bounded summary into a message or tool result.

Sources: run.js, search_history, expand_history, file access rules.

2. The five layers that people often call “context”

A context window is the model’s bounded input-and-response working space for one request. The host constructs what goes into that space. The complete conversation accumulated over a long session can be much larger than the selected material in a particular request.

1 · Canonical history
The host’s retained messages: user text, assistant responses, tool calls, and tool results.
↓ select, shorten, summarize when needed
2 · Request projection
A per-request view of history, possibly with shortened old results, a checkpoint digest, an objective reminder, and an index of hidden exchanges.
↓ add system instructions, tool definitions, cache annotations, model controls
3 · Runner request body
The actual JavaScript object built for the bridge. Captured at runner_model_request_built.
↓ bridge processing
4 · Transformed upstream request
The bridge resolves the model and adjusts the system field before forwarding. Captured at bridge_request_transformed.
↓ remote model processes request
5 · Response and subsequent tool execution
Returned content and tool results extend canonical history; the next step builds a new request.

Canonical means the host’s retained reference history. A projection is the selected view sent for a particular step. A request body is the structured data sent over the connection. None of these is the model’s internal state of attention, neuron activations, or a complete record of hidden reasoning.

The source intentionally keeps lossy request shaping out of the canonical message array. This lets the host show less old material now while retaining it for later retrieval. “Lossless” is relative to what entered that history: a file read that returned only a page never supplied the omitted pages, and old sessions saved under earlier compaction behavior cannot recreate already discarded text.

The system prompt and tool definitions are separate from the canonical messages. Searching history is therefore not equivalent to asking “show every byte of my current system prompt and available tool schema.” A schema is the field definition that tells a model how to call a tool.

Sources: projection ownership and stages, final request construction, bridge transformation order, legacy-history handling.

5. How close is a trace to the actual context window?

For “what did the runner intend to send at step N?”, the most direct event is runner_model_request_built. It is recorded after projection, cache annotations, and message-contract validation, immediately before the network call. At payload-capturing levels it contains the built request’s system, messages, tools, model, and output controls.

For “what did the bridge prepare for the upstream model?”, inspect the matching bridge_request_transformed event. The bridge first logs the incoming request, then resolves the model, defaults the response allowance if needed, and reshapes the system field. The transformed body is then passed to the proxy. Thus the runner-side capture alone is not sufficient to describe all bridge-side instruction changes.

Trace level Available information
off No events from that trace instance.
summary Request sizes, counts, tool names, hashes and other event metadata; no captured body payload.
redacted Structured payload capture with scrubbing.
full Payload capture; still processed by redaction before persistence. It is not guaranteed to be byte-identical to the outgoing request.

A useful implementation detail: although captureForLevel(full) is more permissive on strings, JsonlTrace.append() performs another redaction pass over the full event. The saved full trace must therefore be treated as a scrubbed diagnostic copy. Comparing the recorded pre-redaction body hash with a hash recomputed from the saved payload can legitimately differ.

Match records using their local run/trace identifier, turn, boundary, and time. Repeated attempts can share a turn label; do not treat the turn number alone as a universally unique request identity. A request-built event proves construction, not transmission or acceptance. Use bridge lifecycle and response records to establish more of that chain.

The proxy’s response preview is bounded; it is not a complete stream archive. The runner’s response event captures the assembled response when that event is reached, rather than each live text fragment. Cancellation and early exits can leave a different subset of events.

No trace reveals how much attention the model paid to a paragraph, whether it understood a rule, or its entire private computation. Returned thinking blocks, if present, are response content; they are not an instrumentation feed into all model internals.

Sources: request/response trace points, trace capture and append redaction, bridge events, transformation, lifecycle and bounded preview.

6. What the model can inspect during its own run today

The implemented route is the optional history capability group. A capability group is a named set of tools enabled for a run. --capabilities history exposes the two history tools under ordinary capability selection; an exact --tools list takes precedence, so the final advertised tools should be checked.

Tool Behavior Bounds
search_history Case-insensitive literal keyword search over retained user/assistant text, tool inputs and results. Returns ranked snippets and addresses. Default 8 hits; maximum 25; 240-character snippet windows. Up to 12 query terms, each at least 2 characters.
expand_history Returns a selected entry or message by tool-call identifier or address such as m12.b0. Large entries are paged with a character offset. Default 20,000 characters; maximum 50,000; minimum page budget 200.

The tools call ctx.getCanonicalMessages(), a closure over the live message array. They do not scan the home folder, depend on trace capture, or require a saved session file to work within the active run. A resumed session can expose whatever history was restored into that array.

A tool-call identifier preferentially resolves to its result; if no result exists it can resolve to the tool input. m12 means canonical message index 12; m12.b0 means its first content block. These are canonical-history addresses, not positions in a shortened request. A displayed range such as m0–m2 is a label, not a supported range-query argument.

History search is not semantic search: a paraphrase can miss a relevant entry. The returned snippets pass through the normal tool-output redaction boundary. Thinking and redacted-thinking blocks are deliberately excluded from the index. Images and documents are represented by placeholders when tool-result content is converted to searchable text; expansion does not recreate those binary contents.

Concrete example: suppose an earlier test returned a long diagnostic report, and the projection now shows only a short marker. The model can search for a distinctive error identifier, get the old tool-call address, and expand the relevant page. This retrieves retained evidence without rerunning the test. If a marker says the file content is stale because a later write changed it, the appropriate action is a fresh file read instead.

There is no model call inside these lookup functions. Their returned text still occupies context and contributes to the next model request’s input. “No model call for search” does not mean unlimited recall is free of context or subsequent token cost.

Sources: search, expansion, addresses and exclusions, multimodal text conversion, visibility precedence.

7. Why reading .bridge-runner is a different capability

The host writes its diagnostic files using its own filesystem functions. The model’s ordinary read_file, search and file-listing routes follow workspace confinement and deny rules. .bridge-runner is explicitly included in the protected directory rules.

I exercised the existing path resolver without reading any log payload. An absolute home trace path was rejected as outside the working directory. A relative project-local .bridge-runner path was rejected by the deny rules. Even using the home folder as the resolver’s working directory did not permit its .bridge-runner child.

The supported distinction is useful: the model can retrieve its own selected historical evidence through a host-provided tool, while broad access to the directory of every session’s records is a separate authority.

My external diagnostic tools in this conversation are not the runner’s tool implementation. My authorized aggregate inspection of this folder does not demonstrate that a model running inside your runner could perform the same operation.

I would not solve context introspection by enabling shell access, changing the working folder, or weakening the directory rule. The existing history tools demonstrate a more precise approach: the host exposes a bounded view of the current session directly. A future context inspector can use that same pattern.

Sources: confinePath / resolveFileTarget / DENY_MATRIX_PATTERNS, read_file, getCanonicalMessages. These are capability descriptions, not a new security audit or a change to the rules.

8. What the runner already knows about context pressure

Before each request, the host estimates input size from the serialized system, tools, and messages. This is an estimator, not an exact tokenizer. It starts from character length divided by four and applies a calibration factor, initially 1.5. Returned usage adjusts that factor for the model when the associated request fingerprint matches.

Observed input occupancy adds input_tokens, cache_read_input_tokens, and cache_creation_input_tokens. A cached prefix still forms part of the request context; caching does not mean those instructions or messages vanish from what the request supplies.

The policy uses the local model catalog, reserves the requested response output, and subtracts a margin of at least 10,000 tokens or one percent of the window. Unknown models use a reported estimated fallback. These are local policy decisions, not independently verified current provider specifications.

Do not use the bridge’s count-tokens route as an exact measurement: the current handler returns a compatibility response of zero. The runner’s working size logic is the local estimator plus response-usage calibration.

The trace’s context_projection event records estimated before/after sizes, thresholds, pressure tier, calibration, canonical message count and bytes, clipping/stubbing counts, checkpoint epoch, and reminder/index presence. The event is also emitted to the output channel. It is not automatically inserted as a complete dashboard into the model’s messages.

Under pressure, the projection can remove superseded old results, keep only the head and tail of large old results, replace older results with reference markers, create a deterministic digest of older raw messages, or reduce one large recent result in an emergency. It protects the recent semantic exchanges—keeping tool calls and results properly grouped. It can also append an objective/task reminder and a short “hidden history” index.

Those digests are built from retained raw exchanges by ordinary code, not an extra summarizing model call on this current path. Old context-compactor.js code exists in the repository; its presence alone does not describe the active request-building path. The current trace reports which projection stages ran.

Two implementation limits to keep in view

The 32-mebibyte canonical-history high-water constant currently sets a diagnostic flag; this projector does not enforce it as a hard memory cap. Also, reminder/index text is added before a final size check; existing review notes discuss edge cases involving hidden-history labels and last-stage overhead. This report does not claim those review findings are fixed.

Sources: estimates and calibration, limits and margins, active shaping path, hidden-history index, count-tokens compatibility handler, existing context review.

9. “Real time” has several meanings here

Surface Write timing in the implementation
Runner trace Synchronous append when the named event occurs. The request event precedes the network call; the response event follows the assembled response and intervening checks.
Session event ledger Synchronous event write with a cursor sidecar update; not a full context snapshot on every append.
Transcript Buffered in groups of 10 events, with explicit final/usage flushes. A file reader can lag behind in-memory activity.
Session state Often saved through a 75-millisecond debounce by default, with explicit flush/save paths. Timing can be configured.
Human log Sections appended when methods are called. Assistant sections use the assembled response, not every streaming fragment.
Archive collector Collects in memory and exports through the finalization path.

A synchronous append makes an event available through the operating system’s file interface; it is not the same as a guarantee that every byte survives sudden power loss. These runner writers should not be confused with the separate Starlark ledger’s synchronized event writes.

There is also an unavoidable one-step boundary. At step 12, the model asks to inspect history. The host executes that tool after receiving the request. The result joins the next request, where projection may make new decisions. Reading a step-12 snapshot cannot itself reveal the exact final step-13 request that will contain the read result.

During an unfinished model response, host-side streaming may show text to the operator, but the response has not yet become an ordinary completed message available for another tool call by that same model. Today’s runner does not provide concurrent self-observation of its own partially generated response through these history tools.

This is why an inspector should say “last built request” or “request for step 12,” rather than vaguely claiming to show “my current context” with no timestamp or request identity.

Sources: buffering, debounced writes, event writes, filesystem primitives, tool and request ordering, archive lifecycle.

10. How to use the existing capabilities without conflating them

For “what did I see earlier?” enable the history capability in the runner’s normal configuration and ask it to use search/expansion. A suitable instruction is: “Find the earlier diagnostic output by its exact error identifier, recover only the relevant page, and state whether it is historical or still current.” This is an example prompt, not a command to paste into Terminal.

For “what did the model receive at that step?” use operator-side inspection of the runner request event and matching transformed bridge event. Check capture level, run identity, turn and event order; inspect only the needed fields. A transcript’s visible conversation alone cannot answer this fully.

For “why did it forget something?” compare the retained message to the actual request projection and its stage metadata. Was the information never loaded, read only partially, clipped, replaced by a digest, stale, or still present? If it was present, the trace still cannot prove why the model failed to use it.

For “how much room remains?” use the named request’s estimate, response reserve, and last matched observed usage. Label estimates as estimates. The cumulative token total for a whole run is not the size of one request’s context window.

If you simply want to find these folders visually, open Finder, select Go → Go to Folder, and paste /Users/alanman/.bridge-runner. The expected result is the directory containing traces, logs, sessions and archive. If it is missing on another Mac, confirm the home folder and how that runner was invoked; the folder is machine-local. No shell command or new live run is needed for this report.

Separate child runs are not one shared mind: the ordinary runner’s spawn_agent explicitly starts the child without the parent conversation and passes a bounded prompt. A parent’s history tool does not automatically index every child session or all files in the home directory.

Sources: child context contract, history capability group, projection and usage flow.

11. What I would add for genuine context self-inspection

Recommendation only—no runtime change is implemented or authorized by this report. Keep history recall and request inspection separate. The former retrieves old evidence; the latter explains which evidence was selected and which request surfaces existed.

  1. A small host-provided context-status tool. Return the last built request’s run/step identity, timestamp, model, estimated input size, response reserve, catalog provenance, message/tool counts, projection stages, checkpoint epoch, and historical observed usage. The reply should name its measurement boundary and avoid copying the whole prompt.
  2. A bounded request-snapshot viewer. Let the model request a specific system section, tool definition, or message page from a host-owned snapshot. Use section identifiers and character budgets. Expose only the current session’s intended diagnostic material, rather than a general filesystem path argument.
  3. A map from retained history to the request. Identify which canonical entries are present verbatim, clipped, stale, or represented by a digest. That directly answers “is this evidence actually in the last request?”—something history search alone cannot establish.
  4. Clear timing and provenance. Distinguish “last built,” “sent,” “response observed,” and “bridge transformed.” Return fingerprints and explicit redaction/truncation markers. Never call a scrubbed snapshot an exact raw-wire replay.
  5. Prevent repeated self-copying. Exclude or summarize prior inspection-tool dumps when appropriate; page targeted sections rather than putting a complete old request inside a new request. Otherwise inspecting context can itself become a major source of context growth.
  6. Keep source text and retrieved text in their proper roles. Historical material should remain quoted evidence, not newly promoted instructions. Signed thinking need not be exposed through the recall interface.

I would start with the small status tool and a canonical-to-projection map. They answer the practical questions with much less input growth than dumping all trace content. A paged snapshot viewer is the next step when precise instruction or schema debugging is needed. A broad log browser adds cross-run complexity and is less focused on understanding the current request.

A synthetic local test should verify that the inspector describes the captured request, that history recall still works after projection, that the system/tools remain distinct from messages, and that the returned inspection result affects only a subsequent request. No new live model campaign is necessary to establish those mechanical contracts; live use would separately test whether the model uses the information well.
