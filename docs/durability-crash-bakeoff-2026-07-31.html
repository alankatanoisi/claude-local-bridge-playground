The question

When a runner process dies mid-task, what does each durability layer retain, and does --resume-session re-execute side effects that already happened? C3's corpus sweep (same date) showed crashes leave pending_effect residue in real ledgers; A1 reproduces the crash on purpose and measures the consequences end to end.

Method

One trial = throwaway workspace + session, a scripted mock bridge issuing three side-effecting write_file calls, one kill, one resume, full forensics. Effect filenames carry the server request number, so a re-executed effect leaves a second file with the same effect number — double-execution is counted from files on disk, never from timing. Matrix: {SIGKILL, SIGTERM} × {debounce 75 ms default, 0 ms control} × three kill triggers (watched on a 2 ms ledger poll) × 3 repeats, run before and after the fix. Clean baseline: 4 requests, 3 effects; clean-completion resume adds exactly 1 request.

Honesty caveat: the mock answers instantly, so an entire run fits inside one 75 ms debounce window — checkpoint loss below is the worst case. The exact invariant: whatever entered the checkpoint during the last debounce window before signal death is lost.

Pre-fix (36 kill trials)

Arm (9 trials each) Stale checkpoint Double-executed effects Resume failed Mean excess requests
SIGKILL, debounce 75 9/9 9/9 0/9 +2.1
SIGTERM, debounce 75 9/9 9/9 0/9 +2.1
SIGKILL, debounce 0 0/9 0/9 8/9 −1.8
SIGTERM, debounce 0 0/9 0/9 7/9 −1.6

Two failure shapes. Default debounce → silent double-execution: the checkpoint died holding only the opening prompt; resume exited 0 but re-executed already-completed side effects, 18/18. Debounce 0 → loud unresumable session: the synchronous checkpoint saved a conversation ending in a dangling tool_use; resume failed the message-contract check and exited 1 after zero requests (hence the negative excess). No double-execution — but only because resume was broken. In both shapes the ledger knew the truth (pending_effect reported, correct repair actions proposed) and nothing on the resume path consults it; applyRepair is a stub (F6). F8 confirmed: SIGTERM rows are identical to SIGKILL rows.

The fix

run.js now installs a SIGTERM handler mirroring SIGINT: it funnels through the run's single idempotent finalizer — synchronous checkpoint flush, run_stopped ledger event, health record, autopsy, exit 143. Node delivers signals on the event loop, after the current synchronous tool batch, so the flushed checkpoint is always contract-valid.

Post-fix (36 kill trials)

Arm (9 trials each) Stale checkpoint Double-executed effects Resume failed Ledger tail
SIGKILL, debounce 75 9/9 9/9 0/9 mid-run
SIGKILL, debounce 0 0/9 0/9 7/9 mid-run
SIGTERM, debounce 75 0/9 0/9 0/9 run_stopped
SIGTERM, debounce 0 0/9 0/9 0/9 run_stopped

All 18 SIGTERM trials: consistent ledger, contract-valid checkpoint, health record written, clean resume with zero double-executions at the cost of exactly one extra request — identical to resuming a cleanly finished session. SIGKILL rows unchanged, as expected: an uncatchable signal can only be survived by better recovery, not handled. Regression check: full suite 799/799.

Comparison arms

LangGraph 1.0.x + SqliteSaver (throwaway uv venv; same protocol; 3 trials): completed nodes preserved exactly-once, the interrupted node re-executed 3/3, resume works by design. That equals our debounce-0 checkpoint currency plus a functioning resume — better than our pre-fix default on both axes, still at-least-once for the step it was killed inside. Our post-fix SIGTERM path beats it for catchable signals; for SIGKILL our runner is currently worse. DBOS: not run — requires Postgres, which is not installed on this machine; its exactly-once claim stays a literature citation.

Findings

ID Finding
A1-F1 F8 confirmed and fixed for SIGTERM (pre-fix SIGTERM ≡ SIGKILL; post-fix 18/18 clean). SIGKILL unchanged by definition.
A1-F2 Default debounce turns crash-resume into silent at-least-twice execution (18/18 pre-fix trials re-executed a completed side effect).
A1-F3 A contract-valid checkpoint ≠ a resumable one: mid-tool checkpoints strand the session on the message-contract check; resume never consults the ledger or planRepair. applyRepair (F6) is the missing bridge.
A1-F4 Replay's orphaned_tool_use detection is dead code on real ledgers — the runner's 10-type ledger vocabulary never includes the message-level events it looks for.
A1-F5 A failed resume leaves a misleading health record: message_contract_error is not in the degraded set, so health says resume_ok immediately after resume failed.

What this feeds

F6 (applyRepair) now has two measured failure shapes it would fix, still deliberately unimplemented this round. The structural recommendation is ledger-aware resume: reconcile the checkpoint against the ledger, which survived byte-perfect in all 74 trials (consistent with C3's 141-ledger corpus, zero corrupt tails). A1-F4/A1-F5 are small testable follow-ups for the concordance backlog.
