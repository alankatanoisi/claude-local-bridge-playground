A1 — Crash-recovery bake-off

Built a mock bridge that does three file writes, then killed the runner on purpose (polite kill vs force-kill) and resumed. Compared with LangGraph’s SQLite checkpointer. Report: docs/durability-crash-bakeoff-2026-07-31.html.

Scenario Before fix After SIGTERM fix
Polite kill (SIGTERM), default 75 ms debounce 18/18 stale checkpoint + silent double-execution 18/18 clean (flush + exit 143)
Force kill (SIGKILL) Uncatchable by design — residual risk remains; resume can still strand or replay
LangGraph SqliteSaver arm Same “replay by design” shape — good company; runner ledger at least detects
What we shipped. src/runner/run.js now handles SIGTERM the same way as Ctrl-C: flush the session checkpoint, write a clean ledger stop event, exit. First process.kill integration tests live in test/runner/ledger-crash-recovery.test.js.

3. Evening — N1 + A3-F1/F2 follow-through

After round 3 we deliberately skipped the big durability repair (F6). Instead we closed three smaller items that do not depend on each other.

ID Problem (in English) Fix
N1 The permission gate only looked at an argument named path. A tool that put its filesystem target under another name would skip the deny-matrix check. Catalog of path-arg keys + gate loops all of them + contract test (path-arg-contract.test.js).
A3-F1 Research-only coordinator runs always exited with code 1, so shell scripts thought they failed even when nothing was wrong. exitCodeForCoordinatorResult — exit 0 when there was no execute phase and no error.
A3-F2 Research workers were stuck at 2,000 output tokens per request. Raising --max-tokens on the coordinator only helped the later execute phase. maxTokens now travels through child inherit; plan JSON can override per node.
