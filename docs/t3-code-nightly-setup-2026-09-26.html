Bridge Runner inside T3 Code (Nightly)

How to make your real T3 Code desktop app start the Bridge Runner as a provider, and a checklist to prove it works. Written 2026-09-26. Replaces the deleted demo dev-stack setup.

1. What this is, in plain words

T3 Code is a desktop app for chatting with coding agents. It has several built-in "provider drivers"; one of them is the Cursor driver. That driver does not know anything about Bridge Runner. It only knows how to start a command-line program and talk to it in ACP (Agent Client Protocol: JSON messages, one per line, over the program's standard input and output).

The driver starts the program twice:

  1. <program> about --format json — "who are you?" A version and identity check.
  2. <program> acp — the real session. It stays running for the whole thread.

The program you point T3 at is the small shell script bin/t3-cursor-shim.sh in this repository. It answers "who are you?", removes a few Cursor-only launch flags, finds a node binary, and hands over to the real ACP agent, bin/local-bridge-acp.js. That agent talks to the local bridge on 127.0.0.1:11437, so every turn spends real model calls through your Claude Code credentials.

Why a "shim" at all? The agent cannot answer "about" itself, and T3 adds flags (--auto-review, --force) meant for the real Cursor command-line tool. The shim is the adapter between what T3 sends and what our agent accepts. It used to live in a T3 fork checkout that has since been deleted; it now lives here, next to the agent it launches.

2. Before you start

Check Where What success looks like
T3 Code Nightly version T3 Code → About 0.0.43-nightly.20260926.2282 or newer (the launch contract was verified against this).
The bridge is running Terminal, any folder curl -s http://127.0.0.1:11437/ping prints a one-line JSON message containing "not_found". That is success: the bridge answered, it just does not know that path. If you see "Connection refused", start the Claude Local Bridge extension (press F5 in Cursor or VS Code with the playground folder open).
The shim is executable Terminal, playground folder ls -l bin/t3-cursor-shim.sh starts with -rwxr-xr-x.
Which node to use Terminal, any folder which node. On this Mac it prints /Users/alanman/.local/bin/node. Copy that path; you will paste it into T3 in the next section, because the desktop app does not share your Terminal's search path.

3. Add the provider in T3 (preferred way)

Where: the T3 Code app window.

  1. Open Settings → Providers.
  2. Click Add provider instance.
  3. Driver: Cursor.
  4. Label: Bridge Runner. T3 turns the label into the instance id cursor_bridge_runner; you only need that id if you ever hand-edit the settings file.
  5. Binary path: the absolute path of the shim: 
    /Users/alanman/Developer/claude-local-bridge-playground/bin/t3-cursor-shim.sh
    Do not create a symlink to it: the shim finds the agent relative to its own location.
  6. API endpoint: leave empty.
  7. Environment variables (on the instance card):
    Name Value Why
    BRIDGE_RUNNER_NODE /Users/alanman/.local/bin/node The desktop app's search path may not include node; this tells the shim exactly which one.
    BRIDGE_RUNNER_CAPABILITIES edits Enables file writes. Every write still shows an approval card in T3's supervised mode. Leave this variable out for a read-only instance.
    Leave the "sensitive" checkbox off for both; sensitive values are stored blanked out.
  8. Save. The card should show the instance as ready, with four models: Sonnet 5, Fable 5, Opus 5, Haiku 4.5.
Shell stays off. Setting BRIDGE_RUNNER_CAPABILITIES=shell is refused by the shim on purpose. The only way to let the runner execute commands is to edit the last line of bin/t3-cursor-shim.sh and add --allow-shell by hand. That is deliberate: who may run commands on this machine is decided in a file, not in a settings screen.

4. Hand-edit fallback (only if the UI route fails)

Where: Terminal, then a text editor. T3 re-reads this file automatically about 100 ms after you save.

Back up first. If the file is not valid JSON after your edit, T3 silently drops every provider instance until the file is fixed. 
cp ~/.t3/userdata/settings.json ~/.t3/userdata/settings.json.bak-2026-09-26

Add this block inside the existing "providerInstances" object:

"cursor_bridge_runner": {
  "driver": "cursor",
  "enabled": true,
  "displayName": "Bridge Runner",
  "environment": [
    { "name": "BRIDGE_RUNNER_NODE", "value": "/Users/alanman/.local/bin/node", "sensitive": false },
    { "name": "BRIDGE_RUNNER_CAPABILITIES", "value": "edits", "sensitive": false }
  ],
  "config": {
    "binaryPath": "/Users/alanman/Developer/claude-local-bridge-playground/bin/t3-cursor-shim.sh",
    "apiEndpoint": "",
    "customModels": []
  }
}

Then check the file is still valid JSON before you trust it (Terminal, any folder):

node -e 'JSON.parse(require("fs").readFileSync(process.argv[1], "utf8")); console.log("valid JSON")' ~/.t3/userdata/settings.json

Success: it prints valid JSON. If it prints an error, restore the backup and try again.

5. Verification checklist

Start a new thread in T3, pick the Bridge Runner provider, and keep the thread in supervised mode. (T3's "full access" mode approves writes automatically on the client side, which would hide the approval card you want to see.)

# Prompt What you should see
1 Count from 1 to 30, one number per line. Lines appear progressively (streaming). If the whole answer paints at once, turn on T3's "Stream token by token (legacy)" setting.
2 Same prompt, then press Stop half-way. The turn ends promptly, the thread is still usable, and the next prompt answers normally.
3 Create a file named hello-from-t3.txt containing the word hi. An approval card appears. Approve once. The file exists in the thread's folder. Delete it afterwards. (Needs BRIDGE_RUNNER_CAPABILITIES=edits.)
4 In a scratch folder containing util-a.js and util-b.js (both with a // VERSION 1 header):
Update the version header comment in the util file. 		A question card asks which file (the prompt is deliberately ambiguous). Answer it; the chosen file is edited after an approval card. Repeat and press Stop on the card instead: the model reports that no answer was given and does not guess.

6. Health check from Terminal (no T3 needed)

Where: Terminal, from the playground folder. Real spend: two tiny prompts, the first cancelled early.

cd /Users/alanman/Developer/claude-local-bridge-playground
node scripts/acp-live-probe.js

It launches the shim exactly as T3 does, runs the ACP handshake, streams a long answer, cancels it mid-way, checks the bridge is still alive, and asks a second question on the same session. A passing run ends with RESULT: PASS, for example: 

[   0.009s] about     ok — cliVersion 2026.09.26-bridge-runner-nightly, userEmail bridge-runner@localhost
[   0.100s] baseline  bridge alive at http://127.0.0.1:11437 (pid 25888)
[   0.251s] handshake ok — session ses_…, 4 models
[   2.9xxs] stream    first chunk after 2xxx ms; session/cancel sent
[   3.1xxs] cancel    stopReason cancelled 2xx ms after session/cancel
[   3.2xxs] survive   bridge alive at http://127.0.0.1:11437 (pid 25888)
[   5.xxxs] session   second prompt answered on the same session (end_turn, "alive")
[   5.xxxs] exit      agent exited 0 after stdin closed
RESULT: PASS
Run it from your own Terminal, not from inside a coding-agent session. Agent sessions (Claude Code, Cursor) run commands in a sandbox that child processes inherit; the runner then cannot write under ~/.bridge-runner and the probe fails with EPERM. The probe prints a hint when it sees that.

7. Troubleshooting

Symptom Likely cause What to do
The thread fails to start; T3 logs show a line beginning t3-cursor-shim: The shim stopped on purpose. The line says why (node not found, unexpected launch argument, refused posture). Node not found → set BRIDGE_RUNNER_NODE on the instance. Unexpected argument → T3 changed its launch contract; the shim's comment block lists the tokens it knows.
Every turn fails with "Bridge returned HTTP 500 … proxies: PROXY 127.0.0.1:…" The bridge (inside the Cursor or VS Code window that runs the extension) inherited a proxy address that nothing is listening on. A running process cannot change its environment. Close the window titled [Extension Development Host] and press F5 again from a normal editor window with the playground open. If it persists, quit and reopen the editor itself.
The model list looks stale after you changed something T3 caches the model list for 30 minutes, keyed by the shim's cliVersion. Wait, restart T3, or bump the date in the shim's cliVersion.
"A turn is already running" The agent handles one turn per process at a time. Press Stop and wait for the turn to end.
All provider instances vanished from Settings settings.json is no longer valid JSON. Restore the backup from section 4.

8. Known limits (accepted for now)

  • Auto effort does not appear in T3's reasoning dropdown: the packaged app drops any value other than low/medium/high/xhigh/max. The fork commit that fixed this (100b3890a) cannot apply to a packaged build. Pick a level, or leave the dropdown alone and the runner's default applies.
  • Reopened threads start with empty scrollback; the session state itself is restored.
  • Shell is off and can only be enabled by hand-editing the shim (see section 3).

9. Removing it

Delete the instance in Settings → Providers, or remove the JSON block from section 4. The shim and the agent stay in the repository; nothing else was installed.
