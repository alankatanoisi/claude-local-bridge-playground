Bridge Runner · runtime audit

Compaction & context-management behaviour under max-settings

Scope: src/runner/context-compactor.js, src/runner/context-budget.js, the turn loop in src/runner/run.js, presets in bin/local-bridge-runner.js, and src/runner/session-health.js.
Scenario modelled: high --max-steps, high --max-tokens, a large initial prompt, and repeated large file reads.
Date: 2026-07-26 · Method: static read of the shipped code paths, arithmetic simulation of the trigger conditions, cross-checked against the recorded run in docs/postmortems/2026-07-11-compaction-tool-pairing-postmortem.md.

Verdict

Your instinct is correct, but the mechanism is not the one the knobs suggest. The warnTokens: 80_000 / haltTokens: 160_000 numbers look conservative against a 200k-token window, and reading only those two lines suggests compaction is late, not early. In practice the runner degrades its own working memory much earlier than those numbers imply, for three independent reasons:

  • The clip stage is not gated on token pressure at all. Once the history reaches 24 messages (~step 12), every tool result over 12,000 chars is truncated — including the result produced on the immediately preceding turn, which the model has not yet used.
  • At the warn tier the ladder already runs the lossy stages. Crossing 80k estimated tokens replaces every tool result older than the last 6 semantic exchanges with a stub, and can trigger full extractive summarisation. The effective memory horizon becomes preserveRecentTurns = 6 regardless of how much real window remains.
  • The trigger metric measures the wrong thing. estimateTokens() counts only message text at chars/4 — no system prompt, no tool schemas, no repo-context block, no thinking blocks, and array-form tool_result content collapses to the 15 characters of "[object Object]". Meanwhile the API returns exact usage every turn and the ladder never looks at it.

Two further defects make the damage worse than necessary: compaction output is persisted to the session store (so resume inherits the lobotomy), and the ghost stage mutates the system prompt tail every turn, which destroys prompt caching exactly when the context is largest — which in turn inflates cumulative input_tokens and can trip the misnamed --max-context-tokens "2x" halt.

Net: the loss is real, it starts earlier than intended, it is irreversible, and it is cache-hostile. Nine of the fourteen findings below are fixable without touching the ladder's architecture.

1. What the runner does today

1.1 Call site

Compaction runs once per turn, at the top of the loop, immediately before the request is built (run.js:1209–1244):

const compaction = applyCompactionLadder(messages, system, {
  ...DEFAULT_POLICY, ...(compactionPolicy || {}), compactionGeneration,
});
...
messages = compaction.messages;              // ← in-memory history is replaced
const systemForRequest = compaction.system;  // ← ghost block appended here

There is no post-tool-result check, so a single oversized tool result is only handled on the next turn.

1.3 Actual stage gates

StageFires whenLoss
clip ladder entered — i.e. tokens ≥ warn OR messages.length ≥ 24. No further gate. Truncates any tool result > 12k chars, at any age, including the newest.
sniptokens ≥ warn (or opt-in message count) Replaces every tool result ≥ 200 chars older than the last 6 exchanges with a stub.
costsame gate as snip Stubs reads whose path was later written. Genuinely cheap loss.
ghosttokens ≥ warn OR any lossy stage applied No message loss, but appends a mutable block to the system prompt tail every turn.
summarize tokens ≥ halt OR (tokens ≥ warn AND messages.length ≥ 44) Collapses everything before the last 6 exchanges into ≤30 fragments of ≤120 chars.

Reading order matters: compactor.js:273 is an early-return guard requiring both "under warn" and "under 24 messages". Message count alone therefore still opens the door for clip, even though snipOnMessageCount / ghostOnMessageCount were explicitly defaulted off to prevent message-count-driven compaction.

2. Runtime simulation under max settings

Scenario A — heavy reads (the common case for this repo)

Assume --max-steps 60, a 20k-char initial prompt, and one ~40k-char read/search result per step (read_file defaults to max_bytes: 50000, tools/read-file.js:16; the ingestion summarizer only intervenes above 64,000 bytes, tool-result-summarizers.js:14).

Scenario B — many small turns (matches the recorded incident)

With small tool results, tokens stay well under 80k but message count climbs at 2/step. The 24-message gate opens at step ~12 and clip becomes the only stage that fires — which is exactly what the 2026-07-11 run recorded: "39 clip-only records from steps 13–51", then full summarisation at step 52 once both warn and the 44-message condition were met (postmortems/2026-07-11…md:183, :151). That recorded run is direct empirical confirmation of the entry-gate arithmetic above.

3. Findings

S1 F1 — clip has no pressure gate and no recency exemption

Evidence
context-compactor.js:273 (entry guard), :284 (clip runs unconditionally), :64–92 (no cutoff argument)
Behaviour
From 24 messages onward, every tool_result above 12,000 chars is truncated on every turn — including the result returned by the previous turn's tool call, before the model has acted on it.
Impact
A 50KB read_file becomes ~12KB one turn later. The model reasons about a file it can no longer see, or re-reads it, burning steps. This is the single largest contributor to "lobotomised early".

S1 F2 — the lossy stages run at the warn tier, not the halt tier

Evidence
:291 shouldSnip = overWarnTokens || …, :324 overHaltTokens || (overWarnTokens && messages.length >= ghostAfterMessages + 4)
Behaviour
"Warn" is a misnomer: at 80k estimated tokens the runner immediately performs irreversible stubbing, and with ≥44 messages it performs full extractive summarisation without ever reaching haltTokens.
Impact
Summarisation — the most destructive stage — happens at ~49% real window occupancy. A three-tier ladder collapses into a two-tier one in practice.

S1 F3 — the original task statement and the task checklist are not anchored

Evidence
:230–256 summarizeOldTurns slices from index 0; :239 truncates each head message to 120 chars. run.js:339–344 persists tasks/activeTaskIds to the session store, but no code path re-injects them into the prompt (context-budget.js:76–86 dynamic tail is an empty seam).
Behaviour
After summarisation the user's actual request survives as its first 120 characters, and the manage_tasks checklist survives only as whatever tool_result text happens to be in the preserved tail.
Impact
Classic post-compaction drift: correct-looking work on the wrong objective. The runner's own roadmap lists "verify post-compaction continuity (active task IDs + safety rules persist)" as an unmet item.

S1 F4 — summaries are recursively re-truncated (compounding amnesia)

Evidence
:254 emits the summary as { role:'user', content: <string> }; on the next pass :239 treats it as head content and slices it to 120 chars.
Behaviour
Second summarisation reduces the entire first summary to a 120-character fragment. Third reduces it again. Nothing marks a summary block as non-summarisable.
Impact
On a long run the accumulated project knowledge decays geometrically. This is the difference between "compressed" and "lobotomised".

S1 F5 — the trigger metric is not the quantity that matters

Evidence
:39–62 estimateBlockChars/estimateTokens
Undercounts
  • System prompt excluded (budget up to DEFAULT_CONTEXT_BUDGET_CHARS = 32_000, context-budget.js:16).
  • Tool schemas excluded (~20 full JSON schemas, several thousand tokens).
  • repoContextBlock excluded (run.js:1107, prepended as a system block at run.js:163–173).
  • thinking blocks counted as zero — they carry neither .text, .content, nor .input. With --thinking the estimate can be off by tens of thousands of tokens.
  • Array-form tool_result content (multimodal/image reads) becomes String([{…}]) → "[object Object]" → 15 chars, while clipToolResults correctly uses stringifyToolResultContent for the same data (:70). The two functions disagree about the same bytes.
Also
A second, independent estimator exists with different constants — estimateTokensAdvisory divides by 2 or 3.5 and JSON.stringifys the whole history every turn (loop-autopsy.js:55–69).
Impact
Thresholds are uncalibrated in both directions: too aggressive relative to the window, too permissive relative to real request size. Neither number can be reasoned about by an operator.

S1 F6 — authoritative usage from the API is never fed back

Evidence
run.js:1373 totalUsage = addUsage(totalUsage, response.usage) — exact input_tokens, cache_read_input_tokens, cache_creation_input_tokens are available every turn and are used only for cost/budget accounting, never to calibrate or drive the ladder.
Impact
The runner guesses at a number it is being told exactly. A single-line EWMA calibration of chars→tokens would make every threshold meaningful.

S1 F7 — compaction destroys prompt caching precisely when context is largest

Evidence
:200–228 ghost block text embeds gen=N and a rotating "last 20 tool_use ids" sample; :318 appends it to the system array every compacting turn; run.js:175–179 markLastBlock() puts the runner's system cache_control breakpoint on that mutating block.
Behaviour
Anthropic caching requires an exact prefix match up to the breakpoint. Because the system tail changes each turn, the system breakpoint misses — and so do the tools breakpoint and the message-prefix breakpoint that follow it (run.js:181–186). Summarisation additionally rewrites messages[0], invalidating the entire transcript prefix.
Impact
Every turn in the long phase pays full uncached input price instead of ~0.1x cache-read price. The stage that exists to reduce token cost multiplies it, and inflates cumulative input_tokens — which feeds F8.

S2 F8 — --max-context-tokens measures cumulative spend, not context, and does not configure the compactor

Evidence
bin:418 parses the flag; run.js:1410 contextTokens = totalUsage.input_tokens + totalUsage.output_tokens (cumulative across all turns); run.js:1411 halts at 2 ×; the value is never passed into applyCompactionLadder (run.js:1209).
Behaviour
Help text says "Warn when total tokens exceed budget; halt at 2x budget" (bin:102) but the command builder and README present it as a context control. Combined with F7, a long run inflates cumulative input and hits a hard stop labelled CONTEXT_BUDGET_EXCEEDED that has nothing to do with context occupancy.
Impact
Operators tune the wrong dial; when it fires, the stop reason misdiagnoses the run. Flagged in the 2026-07-11 postmortem (recommendation 3) and still open.

S2 F9 — compaction is destructive to persisted session state

Evidence
run.js:1243 messages = compaction.messages → run.js:1435–1441 persistSession(sessionStore, messages, …) → sessionStore.setMessages(messages) (run.js:337).
Behaviour
Clipped bodies (and, on any successful turn, the summarised collapse) are written into the session file. --resume-session / --fork-from inherit the compacted history. The full tool text still exists in the transcript JSONL, but nothing rehydrates from it.
Impact
Loss is permanent across sessions, not just within the run. The 2026-07-11 note that "the session store was not poisoned" refers to message structure; content loss was already persisted.

S2 F10 — compactionGeneration conflates "compressed" with "unhealthy"

Evidence
:321 and :330 each add +1 per turn; session-health.js:17 MAX_COMPACTION_GENERATION = 5; :50–52 marks the session degraded; assertResumeAllowed then blocks resume without --ack-resume-risk.
Behaviour
Three consecutive compacting turns (ghost fires every turn while over warn) are enough to exceed 5. Any healthy long run therefore ends up flagged degraded.
Impact
Health signal becomes noise; operators learn to pass --ack-resume-risk reflexively, which is exactly when it should mean something. It also thrashes the dynamic prompt-cache key (context-budget.js:48–50).

S2 F11 — no preservation priority; the ghost block tells the model nothing actionable

Evidence
:102–122 snip treats every result ≥200 chars identically; :200–218 the ghost block lists tool_use ids.
Behaviour
An error message, a diff that was applied, and an incidental directory listing are all stubbed with equal enthusiasm. The recovery hint the model receives is a list of opaque ids it cannot re-fetch by.
Impact
The model keeps its narrative (assistant text is never compacted) but loses its evidence — the ideal setup for confident hallucination. Ghost should carry paths, tool names, and one-line outcomes, which are directly re-fetchable.

S2 F12 — two inconsistent truncation caps in one pipeline, and no post-tool check

Evidence
tool-result-summarizers.js:14 DEFAULT_SUMMARIZE_THRESHOLD = 64_000 bytes at ingestion (tool-aware, head/tail preserving) vs compactor.js:21 maxToolResultChars = 12_000 one turn later (blind prefix slice).
Behaviour
Bytes are admitted generously by the good, tool-aware summarizer, then cut by the naive one. The ladder only runs pre-request, so an oversized batch of results is never trimmed until the next turn.
Impact
Wasted work, and the surviving 12k is a prefix rather than the semantically useful head+tail the ingestion summarizer would have produced.

S3 F13 — presets are aggressive and are recommended routinely

Evidence
bin:485–496 --task-scope → warn 40k / halt 80k / clip 8k / snipAfter 12 / message-count triggers ON / maxSteps = 8; bin:497–508 --compact-each-turn → warn 20k / halt 40k / clip 4k / snipAfter 6. session-health.js:97 and :105 recommend --task-scope in the standard "next task" tips.
Impact
Reasonable as explicit opt-ins for narrow tasks; harmful if an operator carries them into a long investigation. --compact-each-turn with a 4k clip cap means the model effectively never sees a whole file.

S3 F14 — the repeat-read nudge fights compaction-forced re-reads

Evidence
repeat-tool-detector.js:16–17 threshold 3 / window 12; :51–57 the injected note says "Use the current result … or move to edit/write once you have enough context."
Behaviour
The detector correctly re-arms per compactionGeneration (:89–91) — good design — but the message does not acknowledge that the previous result was deleted by the runner.
Impact
Mild: nudges the model away from a re-read that compaction made necessary.

4. What is already right

  • good Tool-pair integrity. groupSemanticExchanges (message-contract.js:163–194) guarantees compaction cuts only at exchange boundaries, and assertValidAnthropicMessages validates the exact outbound payload (run.js:1257–1273). The 2026-07-11 root cause is properly closed at the boundary, not papered over.
  • good clip is now byte-bounded and idempotent (compactor.js:79–87, plus a regression test) — the "39 clip records" telemetry noise is fixed.
  • good Message-count-only snip/ghost are off by default with an explicit rationale comment (compactor.js:28–34) and a regression test asserting no compaction under low token pressure. The same reasoning simply was not applied to clip (F1).
  • good Cost-aware stale-read drop (compactor.js:153–198) is a genuinely well-designed stage: it drops bytes that are provably useless (reads superseded by later writes to the same path) before touching useful ones.
  • good Observability exists. compaction events, compaction_applied ledger entries, and beginner hints are already wired (run.js:1221–1242) — the plumbing for the metrics recommended below is in place.
  • good Tool-aware ingestion summarizers (tool-result-summarizers.js) run after secret scrubbing and preserve head+tail — the right shape for lossy compression. They are simply under-used relative to blind clipping.

5. Recommendations

Tier 1 — stop the early lobotomy (small, surgical, high payoff)

R1 · Gate clip on pressure and exempt the recent window

Two changes in context-compactor.js. First, do not let message count alone open the ladder for clip; second, give clipToolResults a cutoff and an age-graduated budget.

// :284 — was: unconditional
const shouldClip = overWarnTokens || (p.clipOnMessageCount && overSnipMessageCount);
if (shouldClip) {
  const clip = clipToolResults(current, {
    recentChars: p.maxToolResultCharsRecent, // 32_000
    olderChars: p.maxToolResultChars,        // 12_000
    cutoff: preservedTailCutoff(current, p.preserveRecentTurns),
  });
  …
}

Rule to encode: never truncate a tool result inside preserveRecentTurns. The model must be able to finish using what it just fetched.

R2 · Make thresholds window-relative and measured

Replace absolute warnTokens/haltTokens with fractions of the model's real context window (from model-catalog.js), computed over the whole request:

function estimateRequestTokens({ system, tools, messages, calibration }) { … }

// derived policy
const W = modelContextWindow;      // e.g. 200_000
softTokens = 0.60 * W;             // cheap stages only: cost-aware drop, clip of OLD results
firmTokens = 0.75 * W;             // snip old tool results, ghost marker
hardTokens = 0.85 * W;             // summarize (last resort)

Also fix estimateBlockChars: count thinking/signature, and use stringifyToolResultContent for array content so the estimator and the clipper agree.

R3 · Move summarize behind the hard tier only

Delete the (overWarnTokens && messages.length >= ghostAfterMessages + 4) clause at :324. Summarisation should require real window pressure, never a message count.

R4 · Calibrate against real usage

// after run.js:1373
const realInput = (response.usage.input_tokens || 0) + (response.usage.cache_read_input_tokens || 0);
calibration.update(lastRequestChars / Math.max(1, realInput));  // EWMA chars-per-token
occupancy = realInput / modelContextWindow;                      // authoritative trigger

Use observed occupancy as the primary trigger and the char estimate only as a forward prediction for the turn being built. This alone converts the whole ladder from guesswork to control.

Tier 2 — make the loss survivable

R5 · Pin a session anchor that survives every stage

A bounded, always-present block containing: the original user request (verbatim, up to ~2k chars), the current manage_tasks checklist, files written this run, the last error, and the active plan path. The seam already exists — getCachedDynamicTail/setCachedDynamicTail (context-budget.js:76–86) is documented as reserved for exactly this and is currently empty. ctx.tasks is already persisted (run.js:338–344); it just needs rendering.

R6 · Make summaries append-only and non-recursive

// session-scoped, never re-truncated
summaryLedger.push({ gen, span: [startStep, endStep], text: bounded(entry, 1_500) });
// render as ONE tagged block; skip blocks tagged compaction:summarize when building a new summary

Tag the emitted block (e.g. { _compactionSummary: true }) and have summarizeOldTurns pass it through untouched instead of slicing it to 120 chars.

R7 · Non-destructive compaction + rehydration

Keep two views: rawMessages (persisted, source of truth) and the compacted projection that is sent. Persist the compaction plan, not its output. Then add a cheap recovery path so a stub is a pointer rather than a hole — either a rehydrate(tool_use_id) tool reading from the transcript JSONL, or at minimum make snip stubs name the tool and arguments needed to reproduce the result.

R8 · Rewrite the ghost block to be actionable

Replace the tool_use id sample with: paths read, paths written, tools used, and one-line outcomes, plus an explicit statement of which results were emptied. Regenerate its text only when the generation actually changes (see R9) so it is cache-stable.

Tier 3 — cost, honesty, hygiene

R9 · Protect the cache breakpoints

Invariant to add and test: content before a cache_control breakpoint must not change on a turn where the underlying inputs did not change. Concretely — move the ghost/anchor block out of the system array (append it to the newest user message instead, which is already past the stable-prefix breakpoint at run.js:230–240), or keep it in system but place the breakpoint before it. Also decouple ghost regeneration from per-turn id sampling.

R10 · Split the two token metrics and rename

FlagMeansAction
--max-total-tokenscumulative spend across the run (today's behaviour)new name; keep --max-context-tokens as a deprecated alias
--max-context-tokensper-request occupancy ceilingfeed into the ladder as hardTokens; compare against real input_tokens + cache_read_input_tokens

Update bin help, README.md, docs/runner-quickstart.html, and docs/command-builder.html together — the postmortem's recommendation 3 is still outstanding.

R11 · Decouple health from compaction generation

Count only irreversible stages (snip, summarize) toward generation; ghost is a marker, not damage. Degrade the session on "≥2 full summarisations" or "summarised with unresolved task IDs", not on a counter that a healthy 40-step run trips by design.

R12 · One truncation authority, and a reactive post-tool check

Let the tool-aware ingestion summarizers own byte reduction (head+tail, per-tool semantics) and align their threshold with the compaction cap so bytes are cut once. Run a bounded ladder pass immediately after tool results are appended, so an oversized batch never survives into a request.

R13 · Report compaction honestly

Extend the existing compaction_applied event with tokensBefore, tokensAfter, bytesDropped, resultsStubbed, anchorsPinned, occupancyBefore/After, and add a verbose per-turn line: context 118k/200k (59%) · cache read 104k · stages: cost. Today an operator cannot tell a 5% clip from a 95% amnesia event — both print "Compaction applied".

8. Operator levers available now (no code change)

  • Do not use --task-scope or --compact-each-turn for long investigations. They cut warn to 40k/20k and the clip cap to 8k/4k and switch message-count triggers on.
  • Keep individual tool results under 12,000 chars so clip is a no-op: use read_file with offset/limit/max_bytes, and search_text with a narrow path. Paradoxically, many small reads survive better than one big one.
  • Push exploration into spawn_agent — the child burns its own context and returns a summary, keeping the parent below the warn tier.
  • Checkpoint findings to disk (write_file to a notes file) and keep manage_tasks current. Anything on disk survives compaction; anything only in the transcript does not.
  • Set BRIDGE_RUNNER_SUMMARIZE_THRESHOLD to control ingestion-side truncation with the tool-aware summarizers rather than relying on blind clipping later.
  • Treat a compaction: snip or summarize event as a checkpoint signal: the run is now operating on 6 exchanges of evidence. Finish the current sub-task and start a fresh session with a written handoff rather than pushing on.

Suggested sequencing

  1. Session 1 (unblocks the symptom): R1 + R3 + the estimateBlockChars fixes from R2. Small diffs in one file, plus two tests. This alone moves first loss from step ~8 to step ~20+.
  2. Session 2 (makes loss survivable): R5 anchor block + R6 append-only summaries.
  3. Session 3 (control loop): R2 window-relative tiers + R4 usage calibration + R13 telemetry.
  4. Session 4 (cost + honesty): R9 cache invariant, R10 flag split and docs, R11 health decoupling.
  5. Session 5 (structural): R7 non-destructive persistence + rehydration, R12 single truncation authority and reactive post-tool pass.
