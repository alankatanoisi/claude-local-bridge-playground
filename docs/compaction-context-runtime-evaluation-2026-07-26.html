Bridge Runner · runtime evidence audit

Compaction is not continuously “lobotomizing” the runner—but its lossy path is too blunt, too poorly measured, and permanently contagious.

A critical evaluation of the current runtime under a large initial prompt, repeated large file reads, high --max-steps, and high --max-tokens. This report combines source tracing, focused tests, two live bridge controls, a live eight-read pressure run, an 80-step deterministic soak, current Anthropic documentation, and a line-by-line review of the previous audit.

Executive verdict

Your concern is justified. The runner is not automatically reduced to six turns as soon as it crosses 80k, but it can erase 70%+ of its file evidence in one pass, can later reduce the original task to 120 characters, recursively degrades its own summaries, and writes the lossy projection into successful session checkpoints.

Large initial prompt 74,476 → 108,446

Local estimated tokens versus Anthropic-reported input occupancy. The estimator undercounted by 45.6% and did not compact.

Seven large reads 81,004 → 21,257

Local estimate before versus after clip + ghost: a 73.8% one-pass evidence reduction.

Live continuity control 9 steps · pass

The runner still returned MULTIREAD_CONTINUITY_OK after eight reads. Short-term continuity survived this case.

Current model capacity 1,000,000 input + output tokens

Current Sonnet 5 and Fable 5 use 1M-token context windows and allow up to 128k output tokens. The runner’s fixed 80k/160k policy is not model-aware.

Long-run soak Marker lost at step 26

A deterministic 40k-character-read simulation first summarized at step 26; the original task’s acceptance-criteria marker disappeared. Summaries nested again at steps 45 and 64.

Important nuance: “80k is only 8% of a 1M window” does not by itself prove that a compaction trigger is wrong. Anthropic’s server-side compactor currently defaults to 150k input tokens because very long active contexts can degrade quality. The runner’s real problem is that it guesses the wrong quantity and then applies low-quality, irreversible compression—not simply that it avoids filling the entire window.

Runtime mechanics

The current control loop has four different “token” concepts

Concept Current implementation What it really controls Problem
--max-tokens Sent as request max_tokens Maximum output for one model call Not reserved in context headroom; not validated against the selected model’s max output.
Compactor estimate Selected message characters ÷ 4 Whether clip/snip/ghost/summarize run Excludes system, tools, repo block, thinking, and miscounts structured content.
--max-context-tokens Cumulative input_tokens + output_tokens Warning and stop after 2× It is spend-like, not per-request context; cache token fields are excluded; it does not configure compaction.
Anthropic usage Plain input, cache read, cache creation, output Actual completed request accounting Recorded for budget/cost, but not fed back into the compactor.

Actual default ladder

entry = estimated_message_tokens >= 80_000
     OR messages.length >= 24

clip      = always after entry; every tool result over 12,000 characters
snip      = over 80,000 (but helper also requires more than 24 messages)
cost      = same gate as snip; removes stale reads superseded by writes
ghost     = over 80,000 OR snip/cost changed anything
summarize = over 160,000
         OR (over 80,000 AND messages.length >= 44)
Large-prompt paradox: a single enormous initial user message can be underestimated and sent without action, as the live 108k test showed. Even if it exceeds haltTokens, summarizeOldTurns() cannot cut anything while the history has six or fewer semantic exchanges; it reports summarize_pending and sends the giant prompt anyway. The runner can therefore be too destructive for mature histories and too passive for one giant initial payload.

Ranked findings

What most contributes to the “lobotomized” feeling

S1

F1 · The estimator is neither model-aware nor request-complete

Evidence
context-compactor.js:39–62; live 74,476 estimate versus 108,446 reported input.
Impact
Triggers cannot be interpreted as window occupancy. They may fire too early for a long tool history and too late for a large initial payload.
Extra risk
Current Sonnet/Fable thinking blocks are preserved and count toward context, but the estimator counts neither thinking nor signature.
S1

F2 · Blind clipping can erase the newest evidence before the model ever uses it

Evidence
context-compactor.js:273–289; clipToolResults() has no semantic-age cutoff.
Behavior
Compaction happens before the next model request. A just-returned 50KB read can be reduced to 12,000 characters before Claude receives that result.
Impact
The model either reasons from a prefix, re-reads the file, or confidently fills in missing details.
S1

F3 · Full summaries are extractive fragments, not continuity summaries

Evidence
context-compactor.js:230–255.
Behavior
The original user message contributes only its first 120 characters; at most 30 fragments survive. The task checklist is persisted but never rendered back into model context.
Soak result
An acceptance marker after character 300 vanished at the first summary (step 26).
S1

F4 · Repeated summaries recursively summarize the prior summary

Evidence
The synthetic summary is an ordinary user string; the next pass slices it like any other old message.
Soak result
Full summaries at steps 26, 45, and 64 became nested “summary of summary” prefixes.
Impact
Knowledge quality decays by generation even when the byte length looks stable.
S1

F5 · High max_tokens is not part of headroom planning

Evidence
run.js:1284–1294; the model catalog stores no input/output limits.
Behavior
A 128k output allowance is forwarded, but the compactor makes exactly the same decision as for a 2k allowance.
Impact
The runner neither reserves output space nor rejects an output cap above the selected model’s supported maximum.
S2

F6 · Successful compaction becomes the canonical resumed history

Evidence
run.js:1243 replaces messages; after a successful model response, run.js:1435–1441 persists it.
Nuance
If the compacted request fails before a response, the earlier raw checkpoint can remain intact. The loss is persisted after the next successful response, not at the instant compaction runs.
Impact
Resume and fork inherit clipped/summarized content rather than a reversible request projection.
S2

F7 · Cache churn is real, but conditional

Evidence
Live cache-read tokens fell from 77,530 on step 7 to 0 on the compacted step 8; 31,439 cache-creation tokens appeared.
Cause
Clipping rewrites message content, while the ghost changes the cached system tail when over threshold.
Correction
The previous audit said the ghost mutates every turn. It only appears while the over-warning/lossy conditions hold; after a large drop, later turns may be ghost-free.
S2

F8 · The context flag and command-builder explanation are materially misleading

Evidence
run.js:1408–1433; command-builder.html labels the flag as a compaction threshold.
Behavior
--max-context-tokens tracks cumulative plain input plus output, warns at N, stops at 2N, and never reaches applyCompactionLadder().
Impact
An operator cannot use the UI control to delay or tune compaction, despite being told that it does exactly that.
S2

F9 · Compaction generation becomes a noisy resume blocker

Evidence
session-health.js:17, 40–65.
Soak result
The first full pass raised generation to 3 (ghost + summary); the second raised it to 5, which marks the session degraded.
Impact
A successful long run can be blocked from ordinary resume because marker generations and destructive generations share one counter.
S3

F10 · Telemetry says “compaction applied” without measuring the damage

Evidence
run.js:1221–1241.
Missing
Actual request occupancy, estimated tokens after, characters dropped, results changed, protected exchanges, cache discontinuity, and whether the original task/checklist remain anchored.
Impact
A 2% stale-result cleanup and a 74% evidence collapse look nearly identical to the operator.

What is already solid

  • Tool-pair integrity is now protected. Semantic exchanges are grouped before cutting, and the exact outbound messages are validated locally.
  • Clip is idempotent and bounded. The old repeated-footer growth defect is closed by a regression test.
  • Message-count-only snip and ghost are off by default. Many small turns do not automatically trigger those stages.
  • Cost-aware stale-read removal is principled. It targets read results made obsolete by later writes.
  • Deterministic malformed-history 400s no longer retry. The earlier incident’s retry amplification has been corrected.
  • The default 16-step ceiling limits reachability. Full recursive collapse is mainly a high-step/continued-session risk, though large reads can trigger clip within eight turns.

Recommended improvements

Fix continuity first, measurement second, architecture third

P0 · now

Protect the newest semantic exchanges from clip

Gate clip on real pressure, and never clip a tool_result inside the preserved-recent window. A just-returned read must reach at least one model request byte-for-byte. If a single result is too large to send safely, reduce it at the tool boundary using tool-aware head/tail logic and say so before it enters history.

P0 · now

Pin a compact, non-summarizable session anchor

Render the original objective, acceptance criteria, active task IDs, current plan/handoff path, files changed this run, unresolved errors, and safety constraints into an always-present bounded block. ctx.tasks already exists and is persisted; the dynamic-tail seam already exists but is unused. The anchor must be regenerated from authoritative runner state, not from old prose.

P0 · now

Make summaries durable and non-recursive

Tag summary blocks explicitly. When generating a later summary, carry the prior summary as a protected input or replace it with a deliberate new continuity summary—never slice it to 120 characters as an ordinary user message. Add assertions that the objective and active task IDs survive three generations.

P1 · next

Measure the entire request and store model limits

Extend model-catalog.js with maxInputTokens/contextWindow and maxOutputTokens. Estimate system + repo block + tools + all message block types. For a precise preflight, add a separately approved Anthropic-native token-count path; until then, calibrate the local estimator from completed requests using all three input usage fields. 

// Context occupancy after a completed request:
const inputOccupancy =

  usage.cache_creation_input_tokens;

// Forward safety must also reserve the requested output allowance.
const usableInputCeiling =
  model.contextWindow -

  safetyMargin;
P1 · next

Separate canonical history from the request projection

Persist raw messages/tool results as the source of truth. Build a compacted view for one outbound request, plus a compaction ledger that records which raw spans each stub represents. Resume and fork should be able to rebuild a fresh view or rehydrate a referenced result. This removes “permanently contagious” context loss.

P1 · next

Split context occupancy from cumulative budget

Rename today’s behavior to --max-total-input-tokens or --max-run-tokens. Make --max-context-tokens a real per-request input ceiling that feeds the compactor. Fix the command builder, README, quick start, and help text in the same change. Count cache reads/creates in both context and cost telemetry according to their respective semantics.

P2 · evaluate

Run a bounded experiment with Anthropic-native server-side compaction

Current Sonnet 5/Fable 5 support the beta context_management compaction strategy. It creates a model-written compaction block, preserves a stable system cache boundary, and defaults to a 150k input trigger. This is architecturally aligned with the project’s Anthropic-native Messages direction. It still needs an isolated live canary: confirm the OAuth bridge forwards the beta header and blocks, confirm transcript/session/archive support, aggregate usage.iterations, and keep the current client compactor as a controlled fallback until parity is proven.

P2 · evaluate

Make compaction telemetry explain the loss

Emit inputBefore, inputAfter, estimate error, results clipped/stubbed, characters removed, protected exchanges, summary generation, anchor status, cache-read change, and model/window/output reserve. A human should be able to distinguish “removed one stale listing” from “discarded 74% of evidence” without opening a trace.

Candidate policy for evaluation—not a magic final answer

A safer state machine for the current 1M models

Tier Candidate trigger Allowed actions Forbidden actions
Observe Every request Full-request estimate; cache-aware usage calibration; stale-read detection. Any content mutation.
Soft ~100k measured input Drop provably stale read results; compress redundant listings with tool-aware summaries. Clip recent exchanges; summarize conversation.
Firm ~150k measured input (matches Anthropic server-compaction default) Summarize old tool evidence with paths/outcomes; preserve at least eight exchanges + anchor. Blind prefix clip; recursive extractive summary.
Hard Start A/B at 200k–250k for 1M models, or earlier if eval quality falls; always below output-reserved ceiling One high-quality continuity summary or native server compaction; checkpoint and optionally pause. Message-count-triggered full summary.
Stop / handoff Repeated hard compaction, missing anchor, failed validation, or budget exhaustion Write a bounded handoff; recommend a fresh session. Continue silently on a degraded summary chain.
Why these are starting points: Anthropic’s own default supports 150k as a reasonable quality trigger, while this runner’s local evidence suggests that its 80k heuristic can correspond to roughly 112k–130k actual input on current tokenizers. The deciding metric should be task-continuity evaluations—not how impressively full the 1M window becomes.

What Alan can do today without changing code

Keep long investigations useful until the compactor is improved

  1. Avoid --task-scope and --compact-each-turn for long research/build runs. They lower thresholds, shrink clip caps, and enable message-count loss.
  2. Use a realistic --max-tokens, not the maximum just because it is available. It is output headroom, not session intelligence. Current code does not account for the reserve.
  3. Keep each read result under roughly 12k characters. Prefer read_file paging with a small limit or max_bytes; a result already below the clip cap cannot be damaged by blind clip.
  4. Write durable findings and acceptance criteria to a project note/handoff file. Do not rely on manage_tasks alone: its authoritative state is not currently re-injected after compaction.
  5. Treat snip or summarize as a checkpoint signal. Finish the current bounded subtask, produce a handoff, and start fresh rather than pushing through several recursive generations.
  6. Do not expect --max-context-tokens to delay compaction. Today it is a cumulative usage warning/stop control with misleading naming.
  7. High --max-steps is a reachability multiplier, not a direct memory allocation. More steps let the session reach lossy generations; they do not enlarge the context window.

Assessment boundary

This report evaluated the current local worktree as found. It did not pull because unrelated user/agent changes were present. No bridge/auth/proxy internals were modified. Live tests establish behavior for claude-sonnet-5 through the local bridge on 2026-07-26; they do not prove account-wide support for every model or beta feature.

Overall recommendation: do not “solve” this by merely raising 80k to a huge percentage of the 1M window. First protect new evidence and the task anchor; then measure the complete request and reserve output headroom; then choose between a high-quality client summary and Anthropic-native compaction using continuity evals. Until then, long max-step runs should checkpoint and hand off at the first snip or summarize event.
