⚠ First, one real security issue (not a policy note): a Claude login token is in this repo's public history

What happened. On 2026-08-09, a captured terminal session was committed as docs/5-paste-block-tests/paste-block-3 (commit 2bdc167). It contained a real Claude login token, an OAuth access token: the "key" that proves to Anthropic that requests come from your account. The next day the line was removed from the current file (commit 39ec363). But Git keeps every old version of every file forever, and this repository is public on GitHub, so anyone can still open the old version.

What I verified today, without ever printing or testing the token:

  • GitHub reports the repo as PUBLIC.
  • Commit 2bdc167 is part of the published main history.
  • That commit contains exactly one string of the access-token type (sk-ant-oat01-…). Today's files contain none.
  • GitHub's own secret scanner has raised zero alerts, so it apparently doesn't recognise this token format. Silence from GitHub is not evidence of safety.
  • An audit on 2026-08-10 called this the top priority and said "revoke first". It also recorded that the token "was not printed, tested, revoked, or rewritten". I found no later record that it was ever revoked.

What I suggest (your call; I did none of it):

  1. Revoke it first. This is the step that actually removes the risk. The simplest route: in a Claude Code session, type /logout, then /login again, so your Mac gets fresh tokens. Access tokens of this type are usually short-lived, so it has probably already expired. But "probably" isn't a record. If you want certainty, look in your claude.ai account settings for a "sign out of all sessions" option. I have not verified which exact option invalidates an old token on Anthropic's side.
  2. Then decide about the history. Removing the string from Git history means "rewriting history" plus a "force push": every later commit gets a new ID, and every other copy of the repo (your other laptop, the extra worktrees) has to be re-synced. Once the token is revoked, the leftover text is harmless, so this step is optional.
  3. Optional prevention: turn on GitHub "push protection" for secrets, which is currently off. It blocks a push that contains a recognisable secret.

"Is this scope creep?"

Yes, "scope creep" is the right word. Developers use it for a project whose goals quietly keep expanding until nobody can say what "done" means. A few related terms describe your situation even more precisely:

  • Too much "WIP" (work in progress). Too many things started at once. Each one is fine alone; together they compete for attention and none gets finished.
  • "Open loops." Things that were started and never explicitly closed. An open loop doesn't need to be finished; it needs a decision: finish, park (on purpose, with a note), or retire (stop, with a note).
  • "Doc sprawl." Many documents, each true on the day it was written, with no single place that says what is true today.

The kind reading of your repo: this is a personal research playground, so exploring many directions is the method, and much of what you explored taught you something real. What's missing is a small closing ritual at the end of each exploration. Section "My honest feedback" suggests one.

      Deep dive: the Starlark direction

      You mentioned Starlark specifically, and you're right that you wanted it badly: it got more focused effort than almost anything else. Here is the whole story.

      What it is, in plain English

      Starlark is a small Python-like language made by Google for its build tool. It is deliberately powerless: it can't read files, use the internet, or run programs, and the same input always gives the same output.

      In the lab, an AI "planner" writes a short Starlark program whose only output is a list of jobs: "analyse file X with a file-analyst worker, time limit Y." A separate JavaScript "host" holds all the actual power. It checks every job against strict rules, enforces a dollar budget, runs the "worker" models, logs every step in an append-only journal (the ledger), and asks for a final combined write-up (the synthesis).

      The idea you were testing: code as a plan, not code as an action. In late July's experiments, letting the model write and run real code ("CodeAct") was fast, but it skipped every safety check. Starlark was your answer: let the AI write orchestration code, but give that code zero authority.

      What it proved

      • Five Claude models wrote valid plans.
      • Haiku 4.5 plans well and cheaply; Sonnet 5 is the most reliable worker.
      • Being too wordy (verbosity), not lack of ability, was the main way workers failed.
      • A shared dollar budget works across separate commands.
      • A run can be killed and resumed live without paying again for finished work (3 live trials, about $0.18).
      • The most important finding: the final write-ups are not trustworthy as factual code reviews. A claim-by-claim check found 24 of 101 claims contradicted by the actual code. The same check did surface one real runner bug, which was fixed.

      • Built on main: R1–R7, R9–R11, R13, R14 (see the inventory's STAR-* rows). R8 ("should the everyday runner call Starlark?") was decided no on 2026-08-31; it stays a separate lab. R12 is deferred.

      My honest feedback

      What's going really well

      • The quality bar is high. Real experiments found real bugs. A crash test found that a polite "stop" signal could make work run twice, and it was fixed the same day. The Starlark fidelity check found a real permission-cache bug.
      • The safety foundation held through every pivot. The runner still uses only your Claude Code login, shell stays off unless you ask for it, no web tools were added, and child agents are limited to one level. All of that is still true in the code.
      • The tests are a genuine asset: 1,161 automated checks, plus "false-green" tests that catch tests which pass for the wrong reasons.
      • Your four-seat team works when the relay is followed. The ACP Slice D and charter reviews found and closed real problems.

      The patterns behind the scope creep

      1. Every thread ends with a list of "next steps", and the next thread starts before anyone triages that list. That's how you reach 66 open decisions and 43 handoffs. It peaked in July: the big reviews that month (concordance, safaris, harness review, orchestration study) started 81 items, and 60 of them are still open today. No single choice was wrong; there was just no closing step.
      2. The tracker died quietly on 2026-07-26, and CLAUDE.md absorbed its job. That's doubly costly: Codex and Cursor don't load CLAUDE.md, and every Claude session has to read 437 lines before starting.
      3. Reviews lag exactly where they matter most. Changes to the bridge, your credentials and shell access went in without the Cursor review your own charter requires for those areas.
      4. Work strands across machines. "The tree is the baton" works on one laptop. With two laptops, finished work has twice been stuck on the "other" machine or on a branch: HS-01 and the Starlark Lows.
      5. Built-but-unconnected code accumulates. Four speed modules were never wired in, and some agent docs still describe them as features. A test that proves each feature is reachable from a real command would catch this; it was proposed on 2026-08-06 and never built.

      Five small habits that would fix most of it

      1. One living status board. Start from this CSV, keep CLAUDE.md and AGENTS.md as pointers only, and have every agent update the board when something changes.
      2. A closing ritual for every thread. Before starting something new, give each "next step" one label: do, park (with a reason), or retire (with a reason). Five minutes per thread.
      3. A limit of two active threads at once, for example "ACP polish" plus one research thread. New ideas go on a "someday" list, not into the work queue.
      4. Let GitHub run the tests on every push (Tier 2), so four agents can't silently break main.
      5. An archive rule for handoffs. Once a handoff is superseded, move it to docs/archive/handoffs/. That's a future clean-up day, not today.

      None of this means doing less exploring. It means each exploration ends with a clear sentence about what it taught you and whether it continues.

      Glossary

      Repository (repo)
      The project folder plus its full history, tracked by Git. Yours lives at ~/Developer/claude-local-bridge-playground and on GitHub.
      Commit
      A saved snapshot of changes, with an ID like 2bdc167.
      Branch / merge
      A branch is a separate line of commits. Merging brings a branch's work into main, the line that counts as "the project".
      Push / pull
      Push sends your commits to GitHub; pull fetches other people's (or agents') commits from GitHub.
      Force push / history rewrite
      Replacing commits that are already on GitHub. Every later commit gets a new ID, and other copies of the repo must re-sync. It's only needed to scrub something out of history.
      Worktree
      A second working folder attached to the same repo, usually on a different branch.
      Stash
      Changes set aside temporarily without committing them.
      CI (continuous integration)
      GitHub automatically running your tests on every push.
      OAuth token
      The digital "key" that proves to Anthropic that requests come from your logged-in account.
      Redaction / secret-scrubber
      Code that replaces secrets with [REDACTED] before anything is written to logs or transcripts.
      Deny list
      The runner's list of files and folders its tools must never touch, such as .env, private keys and .ssh.
      Symlink / hardlink
      Files that point to (or share data with) another file. Attackers can use them to trick tools into touching a forbidden file.
      Bridge
      Your VS Code extension at localhost:11437 that lets local programs use your Claude Code login.
      Runner
      Your own coding-agent loop: prompt → model → tool → result → repeat.
      ACP (Agent Client Protocol) / T3 Code
      ACP is a standard way for an app to drive an AI agent. T3 Code is the desktop app that now hosts your runner through it.
      Starlark
      A deliberately powerless, Python-like language, used in your lab to let AI write plans that can't do anything by themselves.
      Ledger
      An append-only journal of everything a run did, used for crash recovery and auditing.
      Golden eval
      A saved "known good" test conversation, replayed to catch changes in behaviour.
      False green
      A test that passes even though the thing it checks is broken.
      Thermo-nuclear review
      Your name for Cursor's deep, after-the-fact review of landed work.
      Handoff
      A dated document one agent writes so the next agent (or you) can pick up the work.
      Opt-in
      Off unless you turn it on with a flag, for example --capabilities history.
      Wired / unwired
      "Wired" code is actually used when you run the program. "Unwired" code exists and has tests, but nothing calls it.
      LaunchAgent
      A macOS background job that runs on a schedule. Yours checks the Claude Code fingerprint weekly.
      Fingerprint
      The set of headers and version details that make bridge requests look like Claude Code's own.
      P0 / P1 / P2, FD, HE, HS, R
      Item-ID families from different reviews. P0 means most serious; FD means Safari "future directions"; HE means the harness-engineering review; HS means false-green "hidden" bugs; R means Starlark recommendations. The inventory's own IDs (SEC-01 etc.) replace them so they can't collide.
