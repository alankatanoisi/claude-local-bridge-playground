Command Builder — Coherence Check and V2

Date: 2026-09-26 · Author: Fable (Claude Code) at Alan's request · Doc type: dated record (findings are as-of this date; the living gates are the tests named below) · Scope: docs/command-builder.html versus the runner and coordinator CLIs as they exist on playground main at 90f50ce.

In one paragraph. The V1 builder was structurally in sync with the runner (every flag it emits is a real flag, capability groups and templates matched, the existing drift gates were green) but eighteen of its rules had drifted from runtime behaviour, three of them safety-relevant: it told you that --dont-ask with shell on "still asks" (the runtime runs shell commands without asking), it validated model effort/thinking with hand-written regexes that disagreed with the model catalog in four families, and its shell-tool checkboxes depended on click history so the same preset could emit a different command the second time. All eighteen are fixed in V1. A combinatorial test suite now checks every generated command against the real CLI (its option table, chaos gate, model validator, and a dead-bridge spawn), so this class of drift fails loudly from now on. A V2 builder was written from scratch around one state object and one pure rule core; it is covered by the same real-CLI checks plus drift tests that pin its mirrored runtime tables to their sources.

1. How the check was done

  1. Read the runner CLI (bin/local-bridge-runner.js: option table, help text, startup validation), the coordinator CLI, and the runtime modules whose behaviour the builder describes: permission modes (src/runner/permissions.js), tool visibility and capability groups, the chaos gate (shell-policy.js), the model catalog and validator, the context policy, session start/resume paths in run.js, trust evaluation, and the prompt registry.
  2. Read the builder's markup and script end to end and compared every rule, tooltip, caution, summary sentence, and preset against those sources.
  3. Wrote a combinatorial sweep that drives the real page script inside the existing fake DOM and feeds each generated command back into the runner's own parseArgs table and startup validators. The sweep found two of the defects below (F5, F8) that reading alone had missed.
  4. Ran the existing gates before and after: builder tests, npm test, npm run lint, npm run check:docs, npm run format:check.

Verified coherent (no change needed)

  • Every flag the builder emits exists in the runner's parseArgs table with the right type; every coordinator flag is covered; retired flags (--resume, --max-context-tokens, --permission-mode, aliases) are never emitted.
  • Capability grouping (whole groups → --capabilities, partial or apply_patch → --tools), the seven-tool core, the hidden apply_patch, and shell/lsp riding their own flags.
  • The chaos gate (--allow-shell --accept-edits --dont-ask needs --chaos-ok) matches validateChaosCombo for all sixteen combinations.
  • Context dependencies (--bare discards opt-ins; CLAUDE.md / repo map need repo-context), template argument syntax, the --test-watch → --allow-shell dependency, coordinator phase ordering and the verify-needs-execute rule, and the caller token never reaching browser storage.

4. V2 — what changed in the re-imagining and why

docs/command-builder-v2.html is a fresh single-file page, not a restyle. The one design decision everything else follows from: one state object, one pure core, many projections. The form writes into the state; Core.derive(state) returns the command, the annotated flag list, blockers, warnings, a plain-language contract, the permission matrix, the effective tool surface, and which controls are inactive and why; the DOM only paints that result. Because the core never touches the DOM, the test suite loads it alone and checks it against the real runner without a fake browser.

Visible differences for Alan

  • Two authority dials instead of one five-way style. Files (Look · Propose · Edit-ask · Edit-auto) and Shell (Off · On-asks · On-unattended) are the runtime's real independent axes (--plan/--accept-edits versus --allow-shell/--dont-ask). V1 had no way to express "auto-approve edits, but ask for each shell command", which is the safest way to run tests; V2 makes it one click. The dangerous corner (auto + unattended) shows an explicit acknowledgement box that emits --chaos-ok.
  • A live permission matrix derived from the runtime's MODES table: for the dials you picked, each tool category reads runs, asks, proposal, or hidden, with the always-ask exceptions spelled out.
  • Mutually exclusive choices are radios. Session start (fresh / continue / resume / fork / restart) and startup context (minimal / project-aware / bare) cannot be put into a conflicting state, so the corresponding V1 conflict panels do not exist.
  • Nothing is erased. A choice whose parent is off is greyed with a one-line reason and returns when the parent is re-enabled (edits under Look-only, CLAUDE.md under minimal context, test-watch under shell-off, worktree under the coordinator).
  • The command is annotated. Each flag is a coloured chip (read / write / shell / danger / orchestration) whose hover text says why it is there; a "Why each flag is here" list and a contract sentence say the same thing in prose. The coordinator engine lists what it cannot accept instead of dropping it silently.
  • Recipes never touch where you work. They patch intent-level fields only; target folder, runner folder, bridge, and trust fields are yours.
  • Share link. The setup can be put in the page address (token excluded) for bookmarking or handing to another agent.
  • Light and dark themes follow the system; no dependencies; canonical --log-level instead of --verbose; tilde-aware quoting; the caller token is never stored.

Deliberately not offered in V2

  • --review-memory, --replay, --repair: maintenance commands, shown as snippets in the side panel rather than as run switches.
  • --permission-mode, --allowed-tools, --template, --max-context-tokens, --resume, --inherit-workspace-trust: aliases, deprecated, or internal. The test that lists them fails if a new runner flag appears that is neither emitted nor on this list.
  • Reverse parsing (paste a command to load the form): out of scope; the share link covers the round trip between people.

Known limits

  • The V2 DOM layer (binding and painting) is not under an automated test; the rules it paints are. On 2026-09-26 it was walked through with a jsdom script (jsdom installed in a temporary folder, not added to the repo): recipes, the acknowledgement box, both dials, greyed-but-kept groups, the engine switch and its omissions list, tilde paths, per-tool exclusion, resume validation, model notes, save, share link, reload from the link, and reset — zero page errors. The same walkthrough exercised V1's worktree checkbox, presets, model greying, and token ceiling. Adding jsdom as a devDependency would let this become a real test; that is a dependency decision for Alan.
  • V1 presets still carry --max-tokens, --stream, and --verbose forward from an earlier preset when the new one does not declare them (display and budget preferences, not authority). Left as is; V2 recipes reset the run-shape fields they own and leave the rest to you by design.
  • Both builders mirror runtime tables by hand. The drift tests make a mismatch fail the suite; they do not make the copies unnecessary. Generating the mirrors from the runtime at build time would remove the duplication (a future slice).
