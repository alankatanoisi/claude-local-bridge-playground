1. The premise is false today — the suite is already red

The task asks what a 100% green run could hide. Before answering that, the honest finding: this repo does not currently produce a 100% green run. On a clean checkout of main, before I changed anything:

tests905
pass901
fail2
todo (known gaps, do not fail the run)1

Two things follow. First, any agent that runs npm test after a change and sees fail 2 has no way to tell its breakage from the pre-existing breakage — so a real regression can hide inside an accepted failure count. Second, both failures are instructive in their own right.

Pre-existing failure #1 — undo restores the WRONG backup live bug

test/runner/undo.test.js › “restores from the newest matching timestamped backup”. undo ranks backups with matches.sort((a, b) => b.mtimeMs - a.mtimeMs). Two backups written microseconds apart get an identical mtimeMs (measured here: both 1786159277413.2898), the comparator returns 0, and the surviving order is whatever readdir() returned — which put the older backup first. undo then restored old-content over the newer save.

This is not a test bug. It is silent data loss in a recovery tool, and it is timing- and filesystem-dependent: on macOS APFS the two writes usually land on different nanosecond stamps, so it passes on Alan's machine and fails here. The tempting “fix” — adding a sleep between the two saveBackup() calls in the test — makes the suite green and leaves the bug. The real fix is a deterministic tie-break: saveBackup() already embeds a monotonic sequence number in the filename, so sort on (mtimeMs, seq). Recorded as HS-03.

It is also intermittent, which is the worst property a failure can have. Across five full-suite runs I measured fail 2 four times and fail 1 once — under load the two writes can straddle a millisecond boundary, the mtimes differ, and the test passes. In isolation it failed 5 out of 5. So this test flips between red and green on the same code, on the same machine, which means an agent could “fix” something unrelated, see the count drop to 1, and conclude it had helped. HS-03 is the deterministic version: it forces the tie with utimesSync so the bug is reproducible on every filesystem.

Pre-existing failure #2 — the bash signal test measures the harness, not the product

test/runner/bash.test.js › “reports signal when process is killed” expects "killed by signal". I traced it: the identical call returns "Command killed by signal SIGABRT" under a bare node process and "Command exited with code 134" under node --test. It is not test order (I replayed all seven preceding cases — still passed) and not the persistent-shell fast path (BRIDGE_RUNNER_PERSISTENT_SHELL is unset). It is the process context: whether the intermediate /bin/sh (dash, here) execs the command — in which case Node sees signal — or forks it, in which case the shell survives and reports exit code 134 (128+6 = SIGABRT).

The false-green risk is the obvious repair: relaxing the assertion to accept "exited with code 134" turns the suite green and leaves the signal-reporting branch permanently unexercised. FG-M6 now guards that branch structurally instead — it fails if the result.signal check is deleted, or reordered after the exit-code check (a killed process can have status: null, so order matters).

Exit-code footgun worth knowing. npm test | tail reports tail's exit code, not the test runner's — my first background run exited 0 while two tests were failing. FG-G8 already guards the npm script against || true; nothing can guard your shell pipeline. Read the # fail line, not the exit code.

2. How I looked for blind spots

A test suite is a set of questions. It goes green either because the answers are right, or because the question was never asked. So rather than reading tests and asking “is this correct?”, I asked: for each realistic near-future change, what would an author edit, and which of those edits changes runtime behaviour without changing any existing assertion?

Three failure shapes drove the catalog:

  1. Unquantified coverage. A point test pins one example (“edit_file asks”). A new sibling added later is outside the net. Fix: sweep the real registry, so future entries are inside the net the moment they register.
  2. Unreachable-but-well-formed additions. The added thing is internally valid and never runs — a catalog entry shadowed by an earlier regex, a capability group with no name, a test file in an unglobbed directory. Fix: reachability assertions.
  3. Detectors that cannot fail. A guard whose offender list is empty because the pattern rotted. Fix: pair every empty-list sweep with a liveness proof against something known to match. This paid for itself immediately (see §5, FG-C11).

I verified each claim by running code, not by reading it. Where a probe of mine was wrong, I corrected it: my first buildSafeEnv probe passed an argument the function does not accept (it reads process.env directly), which made a leak look like a non-leak. Re-tested properly, it is a leak — item BS-31.

7. What I did NOT write, and why

Redundant tests are a cost, not coverage: they add runtime, they add edit surface, and they make the suite look stronger than it is. Three of my drafted checks duplicated existing FG-D guards, so I deleted them and kept only the delta:

DraftedAlready covered byWhat I kept
“DEFAULT_MODEL is known, active and catalog-priced” FG-D10 Only the package.json ↔ catalog cross-check (FG-H7) — the part FG-D10 cannot see, because the two defaults live in different files
“unknown models are not catalog-priced” FG-D11 Only the separation of the two estimate tiers and the no-borrowed-label rule (FG-H9) — FG-D11 treats both estimates as one case
“cost arithmetic matches published rates” FG-D12 FG-H12, kept because it is strictly stronger: FG-D12 bills 1M of every component at once and compares against the sum, which is invariant under any permutation of the four rates. FG-H12 bills each component alone, pinning every rate to its own dimension

I also did not re-test torn ledger tails, cursor-past-EOF, or schema-version fallback — FG-F6…F9 own those, and FG-L deliberately covers only the properties a buffered writer breaks.

8. Verbatim agent prompts for the 5 changes

Copy one block at a time into a fresh agent session. Each is written to be handed to an agent that has not read this report, so each carries its own context. None of them mention the guards by name — that is deliberate: if the prompt named the tests, the agent would code to the test instead of making the change naturally, and you would learn nothing about whether the guards catch a realistic implementation.

After the agent finishes, run this yourself: npm test then npm run lint then npm run format:check. Expect the two pre-existing failures described in §1 and the four registered todo entries. Any other failure is the guard catching the change.

HC-4 — retry failed coordinator workers (the A3-F4 residual)

Paste block — HC-4
Close A3-F4: make the coordinator retry workers that fail, instead of letting a single
transient failure lose a whole phase.

Requirements:

     (3 attempts total). Make the attempt count configurable with a `--worker-retries`
     flag, default 2.

     budget invariant must continue to hold: the sum of active leases plus recorded usage
     never exceeds the parent caps. Read src/runner/budget-broker.js and the lease
     handling in src/runner/coordinator.js before you start, and say in comments how your
     retry path preserves that invariant.
  5. Record retries in the run result so a field test can see how many happened.

the real output. Do not weaken or delete an existing test to make the suite pass; if a

10. Glossary

False green
A test run that reports success while the thing you cared about is broken — usually because no test ever asked the relevant question.
Change-detector test
A test that pins current behaviour so any change to it must be deliberate. It does not prove the behaviour is right; it proves nobody changed it by accident. Several guards here are openly change-detectors and say so.
Liveness proof
A companion check that a detector still recognises something it definitely should. Without one, a sweep that reports “no offenders” cannot be distinguished from a sweep that is broken.
Vacuous pass
A test that passes because its assertion never really ran — an unawaited async assertion, an empty offender list from a rotted pattern, or a case with no assertion at all.
todo vs skip
Both are ways a test stops protecting you. A todo test runs and prints not ok but does not fail the run — good for recording a known gap. A skipped test does not run and prints ok — which is why it is more dangerous, and why FG-M4 now registers them.
First-match-wins
The model catalog is scanned in order and the first matching pattern is returned. That is why a more specific entry must be placed before a broader one, not appended at the end.
Lease (budget)
A reservation of tokens a parent run sets aside for a child worker, so two children cannot both spend the same remaining budget. Reserved tokens must be returned (“released”) whether the child succeeds or fails.
Ledger / cursor
The ledger is an append-only log of what a run did, one JSON object per line. The cursor is a small sidecar file recording how far along the ledger the run had got, so resuming does not have to re-read the whole file.
Sink
Anywhere bytes leave the program and persist or become visible — a file, stdout, a network request. Every sink must pass through the redaction boundary so secrets are scrubbed.
Egress
Outbound network access. The runner has none today except the model client, which is why adding it is a distinct risk class.
