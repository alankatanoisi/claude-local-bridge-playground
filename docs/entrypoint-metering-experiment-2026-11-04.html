Subscription Meter Experiment

2026-11-04 · Fable (Claude Code) with Alan · playground main · live spend $32.98 at list prices (cap $40) · raw data under ~/.bridge-runner/experiments/entrypoint-metering-2026-11-04/ (not in git)

Question. Every request the bridge sends draws on the Claude plan's 5-hour usage window. How much window does one request cost, per model, and does the bridge draw the window at the same rate as Claude Code's own headless mode (claude -p) on the same account?

1. Headline numbers

Each row is one complete interval: the tokens and list-price dollars that passed between two consecutive one-percent steps of the 5-hour meter, with nothing else known to be using the account. "Prompt tokens" is everything on the input side (plain input plus cache writes). Output was held to a few tokens per request.

The two Haiku bridge intervals agree to 0.05%, and the two Sonnet bridge intervals to 3%, which is the strongest sign the account was quiet while they ran.

2. What "one-percent tick" means and why it is the method

Anthropic answers every OAuth request with headers that describe the plan's usage windows. The two that matter here are anthropic-ratelimit-unified-5h-utilization and the 7-day twin. Their value has two decimals: 0.15 means 15% of the window is used. A single request never changes the number, so the only measurable quantity is how much usage passes between two consecutive steps. The probe sends equal-sized requests, reads the meter from each response, and when the value steps from 0.19 to 0.20 and then from 0.20 to 0.21, the tokens sent in between are the cost of exactly one percent of the window. The request that crosses a step is counted as the first request of the next interval.

Partial intervals (before the first tick seen, or after the last) are discarded; the raw files keep them. The probe also records a tick whose value goes down as a window reset; none occurred (the window reset at 17:50 UTC, after the last run ended at 17:32 UTC).

3. Instruments that landed in the repo

src/proxy.js — meter headers forwarded and traced
Every upstream header under the anthropic-ratelimit-unified- prefix is now forwarded to the local caller and recorded as a new upstream_subscription_meter trace event with its values. Before this the bridge recorded only header names and forwarded only the API-style request and token limits. anthropic-organization-id and anthropic-workspace-id stay unforwarded; the new test in test/anthropic.integration.test.js checks both directions.
src/runner/model-client.js — meter in runner response metadata
The runner's per-turn response metadata now carries the 5-hour and 7-day utilization and status, so a run's own trace shows what each turn cost the plan.
scripts/meter-probe.js — the probe
One arm per invocation. --arm bridge posts to a bridge (default: a lab copy on port 11477) and reads the meter from the forwarded headers. --arm print runs one claude -p process per request with the session-marker variables removed and the entrypoint pinned to print mode's own default, and reads the meter from its rate_limit_event and the tokens from result.modelUsage. Claude Code's own list-price total_cost_usd matched the probe's price table to the cent on every run. Each request carries fresh inventory-style filler so no two prompts share a cacheable prefix; refusals and HTTP errors are recorded and excluded from intervals; a shared ledger enforces the session budget cap.

The bridge under test was a standalone copy started from the working tree (node bin/local-bridge-standalone.js on port 11477, reading the Keychain login), so the VS Code bridge and the Claude Code session that ran the experiment were untouched.

5. Observations

  1. The meter is neither pure tokens nor pure list price. Through the bridge, one percent costs about 9.4M Haiku tokens, 0.63M Sonnet tokens, or 0.39M Opus tokens. In list dollars that is $0.94, $1.26 and $1.57. List input prices span 40x across the three models; the meter spans 1.7x in dollars and 24x in tokens. Relative to list price, Haiku tokens weigh about 1.7x more than Opus tokens on this meter, and Sonnet about 1.25x more.
  2. Bridge and headless Claude Code draw the window at similar token rates on every model. Per one percent, claude -p needed 0.80x (Haiku), 0.79x (Sonnet) and 0.88x (Opus) of the prompt tokens the bridge needed. Its tokens are cache writes, which list at 2x plain input, yet the meter gap is far smaller than 2x. The incomplete cache-user bridge arm points the same way: after its only tick, 291,808 cache-write tokens ($2.34) passed without reaching the next one, versus 391,803 plain tokens per percent on the same model. The data are consistent with "same path cost, slightly heavier weighting for cache writes", but the cache-user arm did not complete, so that reading is supported, not proven.
  3. The weekly meter moved three steps (0.11 → 0.14) while the 5-hour meter moved 22 steps (0.17 → 0.39) over the whole experiment. Read coarsely, this account's 7-day window is about seven times the 5-hour window.
  4. Haiku's safety classifier declined the first filler. A wall of random nature words was refused with category bio on both arms; inventory-style lines were never refused. Refusals carry stop_reason: refusal with zero output and are excluded from every interval because whether a declined request is metered is unknown.
  5. Claude Code's own cost figure is list price. result.total_cost_usd equals the probe's independent computation on every run, with 1-hour cache writes at 2x input and the model's cache-read rate.

6. Not measured, and other limits

  • No interactive or VS Code session rate was measured. Both arms carried the print-mode label. The experiment therefore says how our bridge compares with Claude Code's headless mode on this account; it says nothing about other labels.
  • Output-heavy requests were not run. All intervals are input-side costs; how output tokens weigh on the meter is open.
  • One interval each for Opus (bridge) and for all three claude -p models. Two for Haiku and Sonnet on the bridge. The cache-user bridge arm has a lower bound only.
  • External use of the same account during a run would shorten an interval. The runs were done while the Claude Code session that drove them sat idle; usage from elsewhere cannot be excluded, only inferred absent from the repeat agreement.
  • Haiku 5.5 doubles its input price above 100k prompt tokens; all Haiku requests stayed near 50k.

8. Reproduce

In Terminal, from the repo root, with a lab bridge running on 11477:

node bin/local-bridge-standalone.js --config /path/to/standalone.json --state-dir /path/to/state
# standalone.json: { "port": 11477, "requireCallerAuth": false }

node scripts/meter-probe.js --arm bridge --model claude-haiku-5-5 --input-tokens 50000 \
  --intervals 2 --max-usd 1.5 --out ~/.bridge-runner/experiments/x/bridge-haiku.jsonl \
  --ledger ~/.bridge-runner/experiments/x/ledger.jsonl --budget-cap 40

node scripts/meter-probe.js --arm print --model claude-opus-5-5 --input-tokens 5000 \
  --intervals 1 --max-usd 5 --print-cwd /tmp/probe-cwd --out ~/.bridge-runner/experiments/x/print-opus.jsonl \
  --ledger ~/.bridge-runner/experiments/x/ledger.jsonl --budget-cap 40

Success looks like a line ending in <-- TICK 0.19 -> 0.2 and a final summary with one row per complete interval. Run arms one at a time: the meter is shared.
