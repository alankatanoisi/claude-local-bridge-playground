Findings

  1. C3-1 — Physical durability is perfect in this corpus: 0 corrupt tails, 0 replay errors.
  2. C3-2 — The guard asymmetry diverges on 60 real ledgers; candidate fix (not made this round): give _loadLastSeq() the same effectId guard as append().
  3. C3-3 — Replay inherits the unguarded rule; repair tooling fed those counts would over-repair.
  4. C3-4 — applyRepair remains a stub (F6, documented not fixed) — currently safer than a real implementation fed 45%-phantom input.
  5. C3-5 — 84 of 141 ledgers have no state checkpoint, so ledger-only recovery is the majority case in the real corpus.

Implication for A1

The durability risk is not ledger corruption — it is the debounced state.json checkpoint losing writes on signal death while the synchronous ledger survives (F8). A healthy modern session shows zero pending intents, so any pending intent after a kill -9 is signal, not noise — but a repair experiment must reconcile the two pending rules first.
