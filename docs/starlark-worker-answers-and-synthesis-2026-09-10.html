1. Where the answer actually lands

Each worker returns its answer to the JavaScript host as structured text. The host validates it, saves it, and collects it with the other results. Once worker execution and any recovery round finish, the host asks a separate model call to write the combined answer.

There are three different “returns” here, and keeping them separate makes the architecture much easier to understand.

Return What comes back Who receives it
Starlark finishes planning A list of job descriptions: what to analyze, which approved worker to use, and which input to supply. The JavaScript host, through the Go evaluator’s output.
A worker finishes its assignment A compact JSON answer: summary, claims, evidence, and confidence. The host’s coordinator, through a provider adapter.
Synthesis finishes A combined prose answer. The coordinator, which stores it in the run’s result files.

The host is ordinary software running locally, not a model with its own mind. It owns the sequence of operations and the records. The planner and synthesizer are model roles that this software calls when needed. Even when those roles use the same model identifier, they are separate requests with separately constructed context.

JSON means JavaScript Object Notation: a text format containing named fields that software can read predictably. A provider adapter is the small piece of code that translates a host request into a provider call and brings the response back.

Source: PhasedCoordinator.runPhases / runJobs, WorkerRegistry.execute, runSynthesis.

2. What “Starlark-bound workers” means today

I interpret your phrase as the bounded worker jobs in our starlark-host/ phased-hybrid laboratory. “Phased” means the host moves through distinct stages; “hybrid” means models make some judgments while ordinary code controls execution.

These workers are currently bounded analysis calls, rather than miniature copies of a full coding-agent session. The bridge builds each request with a system instruction and one user message. This host does not give the worker an iterative tool loop, a shared chat transcript, or a mechanism to recursively spawn more workers. A worker cannot browse the rest of the repository through this call.

Starlark is used as a restricted programming language for producing a plan. Its evaluator receives document metadata—such as identifiers, paths, sizes, and fingerprints—and returns data. The evaluator has no model, filesystem, network, or shell functions. It does not remain suspended waiting for worker callbacks.

Current scope versus future runtime: the recorded owner decision keeps Starlark as a separate lab with its own command-line entry point. There is no Starlark run_workflow integration edge in the main runner. This report explains the implemented lab as the concrete foundation for your runtime discussion; a future parent-agent handoff is identified separately below.

The lab also has a host_json planning option. That creates the same validated job descriptions directly in JavaScript without generating or executing Starlark. It preserves the worker-return and synthesis mechanism, so those mechanisms are not dependent on Starlark syntax.

Sources: lab README, ClaudeBridge.call, evaluateStarlark, owner-decision banner, later implementation record.

3. Follow one fan-out from start to finish

A fan-out splits one objective into several independent jobs. A fan-in collects their results again. Picture a research coordinator handing different pages to several readers, receiving their standardized notes, and then commissioning an editor to write the overall explanation.

Host collects inputs. Repository discovery chooses allowed files and saves the supplied input bytes.
↓
Planner → Starlark evaluator → host validator. A proposed job list must satisfy the host’s limits.
↓
Host dispatches worker A · worker B · worker C … Each receives its assignment and explicitly selected source content.
↓
Each response returns to its waiting host call. Parse answer → save artifact → append success receipt. Rejected answers become failure records.
↓
Host waits for the phase. If jobs failed, an eligible recovery plan may run a second worker round.
↓
Host constructs synthesis context. Compact accepted answers and failure records go to one synthesis call or grouped summary calls.
↓
Final prose returns to the host. Save synthesis artifact, result state, and completion evidence; return a status summary to the caller.

In the current repository fan-out configuration, the collector selects at most six JavaScript files under src/runner. Each selected file gets exactly one initial job. The configured concurrency is two: at most two worker calls run at the same time, with remaining jobs waiting their turn. Six jobs therefore does not mean six simultaneous model calls. Individual files are bounded at 40,000 bytes, and the collection at 180,000 bytes.

Jobs may finish in any order. The event log reflects when events occur; the returned result array retains the original job-list order because the host places each answer in its assigned array position. Recovery results are appended after the initial results. Synthesis waits for the worker phase and the recovery phase; it does not update a final answer continuously as individual workers finish.

Sources: prepareWorkflowDocuments / runWorkflow, runJobs / mapConcurrent / runPhases, current configuration.

4. Exactly what a worker hands back

The transport returns a response envelope—an outer container—with fields such as text, token usage, cost, and a stop reason. The coordinator parses the text as the worker’s actual answer. A token is a small unit of text used in a model’s input and output limits; it is not the same thing as one character or one word. 

{
  "summary": "The supplied file coordinates a bounded queue of jobs.",
  "claims": ["Only the supplied file was inspected."],
  "evidence": ["The supplied excerpt stores results at their job indices."],
  "confidence": 0.8
}

Illustrative answer shape only; this is not a saved worker result or a claim about an uninspected source.

Field Enforced requirement What it tells the host
summary Nonblank string, at most 1,200 characters. The worker’s compressed account.
claims At most four strings, each at most 300 characters. Assertions worth carrying forward.
evidence At most four strings, each at most 300 characters. The worker’s stated support.
confidence Number from 0 to 1. A self-reported rating, not a verified probability.

All four fields must be present and extra fields are rejected. Empty claim and evidence arrays are allowed. The parser tolerates a surrounding JSON code fence, although the prompts request bare JSON. Overlong model output is rejected; this parser does not quietly shorten it. JavaScript string length supplies the character measurement, so the exact implementation counts UTF-16 code units, which can differ from visible characters for some symbols.

The host then adds information the worker does not need to invent: the job description, attempt number, success status, artifact location, usage, and cost. That outer host record connects the answer to the assignment. An artifact is a saved output file; a receipt is a recorded event saying what happened.

Structured does not mean verified. The current parser checks field names, types, and sizes. It does not check whether evidence quotes really occur in the file, whether each claim follows from that evidence, or whether the confidence rating is justified.

Sources: WORKER_OUTPUT_LIMITS, parseWorkerOutput / runJobs, response extraction.

5. How the collected answers become one explanation

The host constructs a new prompt containing the overall objective and compact result records. For a success it passes job_id, attempt, ok: true, and the four-field output. For a failure it passes job_id, attempt, ok: false, and error.

This is a fresh synthesis request. It does not inherit the worker conversations or the planner’s earlier thought process. Normal initial-run synthesis uses the active planner-model tier: the model that most recently produced an accepted planning or recovery program. The worker model can be different. Choosing the same model identifier does not automatically share context.

1–4 recordsOne synthesis request under default automatic selection.
5+ recordsGroups of three results get short summaries; another request combines them.
6 records → 3 callsTwo group summaries plus one final combination, with no retries in this example.

Small collections: one synthesis call

The single call sees the complete compact result set and is allowed up to 2,500 output tokens by default. Its instructions say to use supplied artifacts and failures, distinguish evidence from inference, report incomplete coverage, and never claim that a failed job succeeded.

Larger collections: map-reduce

Map-reduce here means “summarize small groups, then combine their summaries.” The map stage divides the result array into groups of three. Each group receives the objective and its compact results, with a request for at most 200 words and an output ceiling of 900 tokens. The map calls currently run sequentially.

The reduce stage receives the objective, aggregate success/failure counts, and those prose group summaries. It has a default ceiling of 2,500 output tokens. It does not receive the raw worker outputs again. For seven records the default is three map calls plus one reduce call.

These are configurable defaults, not intrinsic rules of Starlark. The 200-word instruction is a model request rather than a separately counted word-limit validator. Group summaries are local in-memory values inside runSynthesis; they are not separate resumable map artifacts. If synthesis is retried, successful workers are reused, but the synthesis operation starts again rather than continuing from a persisted group-summary checkpoint.

The tradeoff: grouping reduces how much material a single call must summarize. It adds another compression step, where qualifiers, evidence details, or relationships across groups can be lost. It does not add an independent reviewer or make the result inherently more accurate.

Sources: DEFAULT_OPTIONS / compactResult / runSynthesis, activePlannerModel and synthesis invocation.

6. What the synthesizer can—and cannot—know

Information Current synthesis visibility
Overall objective Yes, supplied explicitly.
Worker summaries, claims, evidence, confidence Yes in single/map prompts. Reduce sees their group summaries.
Recorded job failures Yes in compact form; reduce sees summaries and counts.
Original full source documents No automatic inclusion.
Full original job descriptions, input identifiers, artifact paths No automatic inclusion in compact records. Workers may mention some details in their own output.
Explicit retry relationship (retry_of) Not carried by compactResult; only job identifier and attempt remain.
Interruption, cancellation, and resume event history No automatic inclusion.
Raw provider traces, usage, and cost records Not included by the synthesis prompt builder.
Other workers’ private reasoning or ongoing messages No such shared conversation in this workflow.

This means “combine the workers’ findings” is a model reasoning task over compressed notes. There is no implemented voting rule, confidence-weighted scoring formula, contradiction detector, source lookup tool, or claim-by-claim verifier in this synthesis stage. If workers disagree, the model can discuss that disagreement only to the extent their supplied notes reveal it; software does not adjudicate it for the model.

The earlier September 7 fidelity review documented both worker mistakes carried forward and details introduced by synthesis. I checked the current prompt builder and validator again for this report: their evidence boundary remains as described above. I did not rerun that historical campaign or independently repeat its entire factual audit today.

My interpretation for the planned runtime: the current design has a clear delivery mechanism, but limited preservation and verification of the evidence behind the final prose. A successful delivery and a correct explanation are separate accomplishments.

Sources: compactResult / buildSynthesisPrompt / validateSynthesisResponse, historical fidelity review, section 4.

7. Failures, retries, and what “completed” means

A malformed worker answer becomes an invalid_worker_output failure, marked retryable. The recovery planner sees failure metadata and can propose retries for eligible failed jobs. The host validates those retry descriptions. On a retry, the host directly supplies the rejection reason to the worker—for example, that its summary exceeded the permitted size—so the worker has something specific to correct.

The current coordinator has an initial worker phase and one recovery worker phase. It does not keep asking for repairs forever. Permanent failures are excluded from the eligible retry set. The recovery planner is not an extra stage that reconciles disagreements between successful workers.

A concrete counting example

Suppose six initial jobs produce five accepted answers and one failed answer. The failed job’s recovery succeeds. The accumulated results now contain seven records: six successes and one historical failure. All six original inputs may have successful coverage, but the original failure remains in the records.

The synthesis prompt and command-line summary count these records. They do not automatically present a deduplicated “final outcome per original input” table. Even the reduce prompt calls the aggregate records “jobs.” Because the compact form omits retry_of, the model has less explicit information for linking that failure to its successful replacement.

When synthesis itself fails

The synthesis validator detects refusal, an output-token ceiling stop, or empty text. These become distinct failure codes with a stage label: single, map, or reduce. A semantic failure gives the run phase: partial and a recorded synthesisFailure. Worker artifacts remain saved. The synthesis-only resume path can retry the prose stage without executing workers again.

Transport errors, such as a thrown network exception, are a separate failure path: runSynthesis does not turn every thrown exception into that semantic-failure object. Do not assume every interrupted or failed synthesis has the same resume state.

phase: completed means the synthesis stage passed its current response checks. Some worker failures may still remain, and the prose has not been fact-checked. Likewise, an event named run_completed is also emitted for semantic synthesis failures with synthesisOk: false; inspect its fields and the stored phase, not its name alone.

Sources: recovery and completion paths, validation and aggregate counting, resumeSynthesis.

8. Where the answer lives on disk—and what the caller receives

A run directory is the local folder containing one experiment’s records. Workflow runs normally live below starlark-host/workflow-runs/; the command prints the precise runDir. These evidence folders are excluded from Git tracking.

File inside the run directory Purpose
artifacts/input-<id>.json Saved input content and metadata for repeatable reconstruction.
artifacts/<job-id>-attempt-<n>.json The accepted four-field worker answer.
events.jsonl Ordered event receipts. JSONL means one JSON object per line.
state.json The latest checkpoint: a saved snapshot of coordinator state.
run-context.json Saved host configuration and execution settings for worker resume.
artifacts/synthesis.json Initial successful synthesis text and the result job identifiers.
artifacts/synthesis-resume.json Successful synthesis-only retry text.
result.json Final stored state, including synthesis, results, phase, and synthesis status.

For ordinary success, the coordinator saves the worker artifact before appending job_succeeded. Event writes are synchronized to disk. Artifact and checkpoint writes use a temporary file followed by rename, so a reader does not ordinarily see a half-written JSON file. That rename mechanism is not the same as synchronizing every artifact and directory to durable storage; do not infer absolute power-loss guarantees from it.

The current command-line caller receives a status summary, not the full final prose. runWorkflow() returns summarizeWorkflow(), and bin/run-workflow.js prints that summary as JSON. It includes counts, phase, synthesis status, and runDir, but no synthesis text field. The coordinator itself returns the full state internally.

So if by “host” you mean a future parent chat agent, there is still a separate integration decision: that parent would need an explicit result-reading or tool-response mechanism. The current lab does not automatically inject the final narrative into a parent conversation. A local file being written does not by itself update a chat.

Sources: RunLedger / atomicWrite, artifact and state writes, summarizeWorkflow, command output.

9. What survives a stopped run

Worker resume reconstructs from accepted plans, saved inputs, terminal event receipts, and artifacts. A recorded success is reused. A recorded failure is also reused so the existing recovery rules remain in charge. A started job with no terminal receipt may run again; that is at-least-once execution, meaning work can repeat after an interruption.

The host verifies recorded plans and available content hashes and refuses malformed or ambiguous reconstruction evidence. A completed run is a no-op on worker resume. A partial run with a semantic synthesis failure is directed to the synthesis-only path.

The important distinction is between “a provider may have done work” and “the host has an accepted success receipt.” They can differ at an interruption boundary. The current source checks for cancellation after bridge response settlement, so received usage can be charged while the corresponding job success is suppressed. Existing review notes discuss that boundary. Do not describe this as exactly-once execution or assume interrupted work is free.

Agent detail: synthesis-only resume has a different evidence path

resumeSynthesis() reads state.json and uses state.results; it does not repeat the worker-resume reconstruction checks. Its default strategy is map-reduce. The command-line wrapper supplies the current generic experiment objective and defaults to the stored initial planner model, rather than necessarily restoring the original workflow objective and last accepted planner tier. Those differences deserve explicit handling in any future reproducibility design; this report does not change them.

Sources: restoreWorkerPhase / runJobs, settlement and abort ordering, synthesis-only implementation, synthesis-only command wrapper, recorded review limitations.

10. My recommendation for a future parent-agent handoff

This section is a design recommendation, not a claim about implemented or newly approved runtime work. I would preserve the current separation of responsibilities, then make the evidence and the final handoff more explicit before broadening worker autonomy.

  1. Return a host-authored result envelope to the parent. Include run identifier, terminal phase, final prose, a coverage summary, unresolved failures, and links or identifiers for supporting artifacts. The parent can then explain both the answer and how complete it is.
  2. Preserve the relationship between original inputs and retries. Carry original job identifier, input identifiers, and retry_of through synthesis. Calculate final coverage in ordinary host code, while retaining the full attempt history separately.
  3. Make evidence references machine-checkable. A claim could point to an input fingerprint and line range or saved excerpt. The host can verify the reference exists. Deciding whether the excerpt supports the claim still requires additional reasoning or review.
  4. Give synthesis a deliberate evidence budget. Attach selected source excerpts where needed, rather than expecting short worker notes to support every cross-file conclusion. For grouped synthesis, preserve claim and evidence identifiers through each group summary.
  5. Separate prose completion from factual review. Display synthesis status and verification status as different fields. Preserve uncertainty and disagreement rather than allowing polished prose to obscure them.
  6. Make retries reproducible. Persist the workflow objective, chosen synthesis model and options, and any intentionally reusable group summaries. A synthesis retry should make any configuration change visible.

For a small experiment, a single synthesis call is easier to inspect because it sees the worker notes directly. Grouped synthesis is useful when the collection becomes too large, but it introduces another place where detail can disappear. A separate evidence-checking pass adds cost and complexity, yet is more relevant to trustworthy conclusions than merely increasing the number of workers.

If workers eventually become full tool-using subagents, the host can retain the same broad return pattern: dispatch → wait → validate → persist → synthesize. Their result contract would need to cover changed files, executed checks, unresolved work, and side effects, and the resume rules would need to account for repeated actions. That is additional design work; the current read-only four-field contract does not provide those guarantees.
