Starlark Workflow Expansion

Implementation handoff · August 6, 2026

Repository fan-out, test-failure triage, provider-neutral workers, and a bounded evaluation matrix

Implemented and verified offline

This slice adds three connected capabilities without changing the bridge runner: bounded repository fan-out, real test-failure collection and triage, and a host-validated Starlark evaluation matrix.

Yes, repository fan-out and provider-neutral workers belong in one slice. Workflows request symbolic workers. A host-owned registry, outside generated code, selects the concrete provider adapter and model.

Authority Flow

Host collector → bounded input documents → planner metadata ↓ generated Starlark descriptors ↓ strict host validation ↓ symbolic worker → host route → provider adapter → concrete worker model ↓ artifacts, ledger, synthesis

Generated Starlark never receives provider credentials, model routes, arbitrary filesystem access, or arbitrary command execution.

Implemented Workflows

Repository fan-out

The host selects at most six JavaScript files under src/runner, with deterministic ordering and per-file and total-byte ceilings. Symlinks, root escapes, common secret locations, private-key files, environment files, dependencies, coverage, and build output are excluded.

Every selected file becomes exactly one independent repo_file_analyst job. The validator rejects added jobs, missing inputs, duplicate coverage, dependencies, unknown workers, provider/model fields, and excessive limits.

Test-failure triage

The host runs one named test suite with an argument array and no shell. The collector confines its working directory, limits executable choice, time, and output, and removes likely credential variables from the subprocess environment.

TAP failures become bounded virtual documents. Each failure becomes one test_failure_triager job that may classify evidence and recommend a diagnostic step, but cannot claim a fix was executed.

Provider-neutral workers

Worker profiles hold behavior and bounds, not providers or models. The current live adapter is the local Claude bridge. The same registry contract can later host Gemini, a local model, a deterministic service, or another runner.

Boundary: this is provider-neutral structure, not yet proof of multi-provider interoperability. Only the Claude bridge adapter has been implemented.
