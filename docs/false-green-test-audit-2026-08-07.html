1. The task and its context

Alan asked three things: (1) list at least 50 blind spots where the runner's test suite could show 100% green while real behavior has regressed — especially right after a code change; (2) write or amend tests so every listed item gets coverage; (3) provide five verbatim prompts, each for a realistic near-future change to this repo, that a different agent will implement on an isolated branch/worktree — after which Alan will run the updated suite against that agent's work.

The suite under audit: 111 test files in test/runner/ covering roughly 70 modules in src/runner/. The suite is genuinely strong on point tests (one tool, one path, one fixture) and on a few process-level tests (the crash bakeoff kills real runner subprocesses). The audit's central finding is a pattern, not a scandal:

The core pattern. Point tests stay green when something new is added wrongly — a new tool, flag, sink, model, or pattern — because nothing iterates over "everything registered." The counter-move is the sweep test: an invariant quantified over the whole catalog/table/pattern-list, so tomorrow's addition is inside the net the moment it registers. Nearly all new tests below are sweeps.

2. Plain-language glossary

False green / false positive green
The test suite passes completely, but a real behavior (often a safety behavior) is broken. The tests aren't lying — they were just never asked the right question.
Point test vs. sweep test
A point test checks one named example ("edit_file asks for confirmation"). A sweep test checks a rule over everything registered ("no write-category tool auto-allows in default mode") so future additions are covered automatically.
Deny matrix
The list of file/directory name patterns the runner must never touch (.env, .ssh/, private keys, credentials…). Lives in src/runner/safety.js.
Redaction / scrubbing
Replacing secrets (API keys, tokens, private-key blocks) with markers like [REDACTED:anthropic_key] before text reaches any log, transcript, or output.
Sink
Any place bytes leave the runner's memory: a transcript file, stdout, a stream, a ledger, a network request. Every sink must scrub. A new sink is the classic leak path.
Ledger / torn tail
The append-only JSONL crash journal per session. A "torn tail" is a half-written last line left behind when the process died mid-write.
todo test
A test that runs and is reported, but whose failure does not fail the suite. Used here to make two known, currently-unfixed bugs permanently visible without blocking CI. When the bug is fixed, the todo flips to a hard assertion in a one-line change.
Worktree
A second folder on disk sharing the same git history but checked out on its own branch — an agent can commit there freely and main in the normal folder is never touched.
Authority ceiling
A frozen snapshot of the run's CLI flags; nothing mid-run (hook, bug, hostile input) may raise authority above it. src/runner/authority.js.

4. Two live bugs found — real behavior, today, not test gaps

HS-01 — Case-variant key-file bypass on case-insensitive filesystems todo test

On macOS's default APFS (case-insensitive), asking the runner to read ID_RSA opens the same on-disk file as id_rsa. But the deny patterns for key files — /^id_rsa/, /^id_ed25519/ — have no /i flag, so the lexical basename check misses the uppercase spelling; and Node's fs.realpathSync (the JS implementation used by cachedRealpathSync) does not canonicalize character case, so the realpath tier misses it too. Net effect: read_file ID_RSA is allowed and reads private-key material. (.ENV is safe — that pattern does carry /i; CREDENTIALS.JSON is safe likewise.)

Fix shape (not applied — reported per Alan's verification rule): add /i to the non-flagged basename patterns, or resolve with fs.realpathSync.native, which returns on-disk canonical case. Encoded as todo test HS-01 in false-green-deny-matrix.test.js; it self-skips on case-sensitive filesystems.

HS-02 — Post-recovery ledger append glues onto the torn tail todo test

SessionLedger correctly skips a torn (half-written) trailing line when re-reading after a crash, and sequence numbering continues correctly. But the append file-descriptor opens in append mode at the raw end of file — so the first record written after recovery is concatenated onto the torn fragment, making both records unparseable to readAll()/replay. Durability math survives; one recovered event becomes invisible to replay and repair tooling.

Fix shape: before the first post-recovery append, newline-terminate the file or truncate the torn tail. Encoded as todo test HS-02 in false-green-contract-durability.test.js. This is directly relevant to the open A1-F4/A1-F5 durability residuals.

8. Accepted risks and uncovered residuals

  • Cross-line Bearer divergence (item 36). Buffered scrubbing can match Bearer\n<token> across a newline; the line-aligned streaming scrubber cannot. Split-invariance still holds (output never depends on chunk boundaries). Documented in the FG-C header; the parity corpus deliberately keeps each secret on one line. Fixing it means a cross-line-aware streaming pass — worth a dedicated slice, not a drive-by.
  • Mocked model transport. Agent-loop tests use scripted mock servers; real Anthropic SSE quirks, retry/backoff timing against a live bridge, and stop_reason variants from real models remain exercised only by transport unit tests. A recorded-wire-fixture harness would be the next step.
  • Golden-eval fixtures are regenerable via --update — a bug can be baked into a new golden and pass. Mitigation is process (review regenerated goldens), not a test.
  • Token-estimation drift: estimateTokens is self-referential (tested against itself, not a real tokenizer). Compaction thresholds inherit that drift.
  • First-run wording assumptions in FG-E. FG-E6/E7 assert trust-gate and transport error text that was reasoned from source but never observed; FG-D7's surface snapshot and FG-D4's core-category expectations are the other likely first-run adjustments. Any adjustment must be reported honestly before fixing (Alan's verification rule).
