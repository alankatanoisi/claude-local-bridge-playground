Starlark Control-Plane Architecture Review

An engineering evaluation of the phased-hybrid Starlark orchestration prototype: what the architecture gets right, where it is structurally at risk, whether Starlark was the optimal language choice versus Python, Java, Go, Rust (and the alternatives that matter more), and fourteen prioritized recommendations.

1. Executive verdict

The architecture is sound, and the Starlark choice is defensible-to-optimal — for the specific slot it occupies. The most important design insight is one the team already made in practice and should now write down as doctrine:

The Starlark layer is not CodeAct. It is code-as-plan, not code-as-action.

The generated program has zero capabilities — no filesystem, network, shell, model calls, or module loading. It can only construct inert job descriptors, which a fail-closed host validator inspects before anything real happens. This sidesteps the exact collision the roadmap review flagged as N-5: CodeAct bypasses every tool-argument-layer path control by construction, but a Starlark plan cannot bypass path controls because it never touches paths — the host-owned repository collector does, inside the existing confinement rules (root ceilings, symlink exclusion, secret-path exclusion). The smolagents lesson ("code actions win") is honored where it is safe — compact, expressive plan generation — while the authority stays exactly where the runner thesis says it belongs: in user-owned host code.

Three structural risks are visible; none is fatal, and all three have precedents in the runner's own round-3 findings:

  1. Two control planes now exist. The native runner stack (coordinator.js, budget-broker.js, session-ledger.js, worker-runtime.js) and the Starlark host both own scheduling, budgets, ledgers, and retries. The architecture diagram honestly labels their relationship "SEPARATE TODAY — no integration edge." Right now drift, not decision, is choosing the outcome (R8).
  2. Budget authority is process-local while the stated ambition (unattended matrices, multi-command campaigns) is cross-process. The $10 gate was maintained manually between commands. Both 08-06 docs flag this as the top gap; this review agrees and ranks it R1.
  3. The prototype lives outside Git, which exempts it from review, CI, and the N-1 reachability doctrine — precisely the conditions that produced the round-3 F1/F2/F5 defect class ("built, exported, unit-tested, never wired"). R3.

3. Was Starlark optimal? Python, Java, Go, Rust — and the alternatives that matter more

First, frame the question correctly: there are two language slots here, and the named alternatives mostly belong to the other slot.

  • Slot A — the language the model generates (the control-plane plan program). Real candidates: Starlark, sandboxed Python, Lua, pure JSON/YAML data, CUE/Dhall, sandboxed JS/WASM.
  • Slot B — the evaluator/host implementation language. Candidates: Go, Rust, Java, Node. The prototype already answers this well: a Node host (matching the rest of the repo) embedding starlark-go as a subprocess. Go is not a competitor to Starlark here — it is Starlark's most mature runtime (the canonical implementation, maintained by the Bazel team). Java (Bazel's original implementation) and starlark-rust (Meta's, used in Buck2) are viable substitutes with no compelling reason to switch today. The subprocess boundary is a feature: a crashed or runaway evaluation cannot take the host down, and OS-level limits back the language-level ceilings.

3.2 Why the general-purpose languages lose Slot A

Python, Java, Go, and Rust are all wrong for the generated-program slot for the same reason: the requirement is a language that cannot do anything. General-purpose languages make you build the "cannot" yourself — sandbox construction, capability stripping, termination policing — and then maintain it forever against a moving runtime. Python is the seductive one (maximum model fluency, the smolagents path), but its correct role in this architecture is the CodeAct worker direction (H1), which the roadmap review already showed must be gated behind sandbox work (N-5) — not the control plane. Compiling and executing model-emitted Go or Rust would add a toolchain, a slow feedback loop, and unbounded capability, in exchange for nothing the descriptor layer needs. Java has the same problem plus JVM weight.

Verdict: keep Starlark — the decision was correct on the evidence, not just on taste

Starlark occupies a rare point in the design space: the only listed option that is simultaneously hermetic by construction, terminating by construction, deterministic, and close enough to Python that even the smallest active Claude tier (Haiku 4.5) generated valid plans first-pass in the live trial. The only real competitors are pure JSON — which you should still use as a cheap path for workflows that need no expansion (see R14) — and CUE/Dhall, which trade materially worse LLM fluency (a higher repair tax) for formal guarantees Starlark already mostly provides. Conditions on the verdict: descriptors (never capabilities) remain the only output; the Go subprocess stays as an isolation boundary; and deterministic linting (R6) absorbs the known "Python-shaped, not Python-identical" failure mode.

4. Fourteen recommendations

Priorities: P0 blocks unattended/paid scaling · P1 do before widening the matrix · P2 strengthens the platform · P3 opportunistic.

R1 P0 — Durable, atomic campaign budget ledger

One append-only budget ledger keyed by campaign ID, with atomic reserve/settle records, shared across processes and commands. Reuse session-ledger.js patterns (sequence numbers, cursor sidecar, atomic state writes) rather than inventing a second scheme — a recorded workspace preference. The manual "reduce the allowance after each command" step must be dead before any unattended matrix runs. This is the one gap both 08-06 documents flag, and it is the correct #1.

R2 P0 — Meter dollars, not tokens

Bind campaign ceilings to cost accounting (estimateCostUsd-style, including cache-read and cache-creation rates), keeping token caps as a secondary dimension. This is the Starlark-host twin of runner finding A3-F4 / roadmap N-3: cache tokens are reported but never counted against ceilings, and the under-count grows with exactly the concurrency being pursued. Fix both planes with the same design so "budget" means one thing everywhere. Regression test: a lease reconciled with cache-heavy usage must move the remaining-budget figure.

R3 P1 — Bring the prototype under version control

Graduate s1-starlark-phased-hybrid out of ~/Developer/orchestration-prototypes/ into Git (playground subtree or a sibling repo). Out-of-git code is exempt from review, CI, and the N-1 reachability doctrine — the exact conditions that produced the round-3 F1/F2/F5 defect class. Keep only genuine throwaway spikes outside Git; this prototype has crossed the "people rely on its results" line.

R4 P1 — Repeated-trial scoring harness before widening the matrix

Implement the live-results doc's own recommended next experiment: at least 5 repetitions per control model on fixed fixtures, scored on a deterministic rubric (first-pass validity, repair success, forbidden-authority attempts, retry correctness, accepted artifacts, synthesis state, latency, cost, trace completeness). Extend golden-eval.js or evals/harbor/ rather than building a third harness — N-2's explicit instruction. Until this exists, single-trial tables must not be quoted as rankings (the doc already models this honesty; keep it).

R5 P1 — Single-source the descriptor policy + a field→enforcement concordance test

Two recurring classes, one fix. (a) One machine-readable schema/limits file generates both the validator's rules and the prompt's policy-disclosure section — killing the finding-1 drift class (policy named but bounds undisclosed). (b) A concordance test asserts every field the validator accepts has a bound enforcement point in the execution path — turning the finding-6 timeout_ms class ("validated but not enforced") into a CI failure instead of a field discovery. This is N-1's reachability idea, specialized to policy fields.

R6 P1 — Deterministic Starlark pre-lint for LLM Python-isms

Before evaluation, run a cheap static pass over generated programs catching known model failure modes: adjacent string literals (observed live, twice), f-strings, while loops, recursion, set literals. Auto-repair the purely mechanical ones; return precise diagnostics for the rest so the model's one repair attempt is guided rather than guessing. Track a per-model "repair tax" metric in the R4 harness — it will likely dominate model choice more than raw capability does.

R7 P1 — Adversarial-program corpus for the evaluator

Live testing exercised honest-but-fallible planners; nothing yet exercises a hostile program. Build a red-team corpus: comprehension bombs (billion-laughs via nested cross products), deep nesting, huge string/list allocation, step-ceiling probes, unicode identifier tricks, and descriptor smuggling (fields that alias or shadow authority fields). Assert ceilings and fail-closed behavior under all of them. This is the permission-safari discipline applied to the new surface — the prototype deserves its own Safari before it grows.

R8 P2 — Decide the runner integration edge deliberately

The diagram says "SEPARATE TODAY — no integration edge." Make that a decision, not drift. Recommended shape: expose validated workflows to the native runner as a capability-gated tool (e.g. run_workflow) that routes through the runner's permission gate and workspace-trust checks, while the Starlark host keeps its own validator (defense in depth, matching the HE-01 pattern). Explicitly reject the alternative — porting the runner's coordinator into the Starlark host — to stop duplicate control-plane growth. Either answer is fine; an undecided answer is not.

R9 P2 — Prove provider-neutrality with a second adapter + contract test

The registry's neutrality is structural, not demonstrated. The cheapest honest second adapter is a deterministic one — a regex/static-analysis service fulfilling repo_file_analyst's exact contract — zero token cost, full contract-coverage value, and it doubles as the W1-style deterministic worker arm. A Gemini adapter can follow. Until then keep saying "provider-neutral structure," never "provider-neutral" (the workflow-expansion doc already models this discipline).

R10 P2 — Terminal-state machine + synthesis-only resume; map-reduce synthesis

Formalize campaign terminal states (completed, partial:model_refusal, partial:truncated_synthesis, failed:*) as an enum with defined transitions. Because worker artifacts are durable, synthesis must be retryable alone — never re-run workers to retry a synthesis. For the truncation class (three ceiling hits live): chunked map-reduce synthesis — compress per-artifact, then combine — instead of one monolithic ceiling-bound call. Synthesis stays independently fallible, but its failures become cheap and recoverable.

R11 P2 — Campaign resume and cancellation kill-tests

Port the A1/F6 discipline to campaigns: kill a live campaign mid-flight, resume from the ledger, and assert completed jobs are not re-run while the interrupted job is at-least-once with intent/result pairing. Separately test cancellation propagation to in-flight worker calls under real concurrency — the abort signal is wired now (finding 6 fix); prove it holds when four workers are in flight.

R12 P2 — Unify evidence layout and end-to-end trace joins

Campaign artifacts should adopt the ~/.bridge-runner unified transcript/index conventions instead of growing a second parallel scheme (a recorded workspace fact). Ensure one campaign ID joins the whole chain: budget ledger ↔ campaign ledger ↔ worker artifacts ↔ runner traces ↔ bridge traces. The five-event bridge correlation already works; extend the join upward so a single ID answers "what did this campaign do and cost" across every store.

R13 P3 — Cost-tiered planner routing with escalation

The live data's most interesting row: Haiku 4.5 passed both planning stages first-attempt at the lowest cost. Make routing policy explicit and evidence-driven: plan with the cheapest tier; escalate one tier only on validation failure after the R6 lint pass. Revisit with R4's repeated-trial data — do not hardcode either reputation or a single-trial result.

R14 P3 — Exploit determinism: golden plans, program hashing, and a JSON cheap path

Starlark's determinism is an asset the prototype has not cashed in yet. (a) Golden-plan tests: snapshot expected descriptor sets per fixture so planner-prompt changes surface as reviewable diffs. (b) Program hashing: hash program + inputs to cache expansions and detect "same plan, different program" drift across models. (c) JSON cheap path: for workflows needing no expansion (small fixed job lists), skip Starlark entirely and accept a plain JSON descriptor list through the same validator — reserve the program layer for where it pays (matrix, Cartesian, and fan-out expansion).
