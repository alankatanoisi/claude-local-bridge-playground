The reports are accurate about our runner. The 2026-07-28 harness engineering review — the one written with full local repo access — is the only document that makes a large number of concrete, checkable claims about us, and it is right on essentially all of them, including the awkward ones. Every line count, every module name, every safety gap it named, and every missing packaging artifact it listed checks out against the current tree.

The two defects worth knowing about are small and both are over-statements of scope, not invented facts.

  • One executive-summary caption mislabels a line count (~13.1k LOC top-level + tools — 13.1k is top-level only; adding tools/ makes it ~16.7k, and the whole src/runner tree is ~19.7k). The report's own appendix states this correctly, so the error is a caption, not an analysis.
  • One finding (HE-03) lists five CLI options as "silently dropped" on the coordinator→kernel path. Four of the five really are dropped; sessionExtract is in fact threaded through.

One important framing point for a non-programmer. The three "AI orchestration" documents are studies of other people's systems. They contain almost no claims about our runner at all — about a dozen sentences total, mostly in the 2026-07-30 review-and-next-steps companion. So "3 of 4 reports were written without broad local permissions" is a smaller problem than it sounds: those three reports mostly did not need local permissions, because they were not describing us. The one that did describe us had full access and used it well.

8. Corrections: where the reports are wrong or imprecise

C1 — Line-count caption (harness review, §1 stat card).

Reads ~13.1k LOC top-level + tools. The true figure for top-level + tools is 16,695; 13,141 is top-level alone; the full src/runner tree is 19,705. The report's own §11 size snapshot lists these correctly and separately, so this is a summary-card slip. It matters only because summary cards are what get copied into later documents.

C2 — HE-03's example list (harness review, §9).

The finding claims capabilities, budgetInputTokens, enableLsp, testWatch, and sessionExtract "can be silently dropped" on the coordinator→kernel path. Four are correct. sessionExtract is in the kernel option map. A better fifth example would be budgetOutputTokens, which is also missing.

C3 — Mis-attribution of effect pairing (orchestration review, §3 table).

Effect pairing is listed under session-ledger.js. It is implemented in tool-pipeline.js; the ledger merely receives the two events.

C4 — Under-specified "redaction misses ghp_".

HE-08b's phrasing (github_pat_, ghs_, Slack xox*, etc.) is correct, but it is worth stating positively what is covered so nobody "fixes" a non-problem: ghp_ and gho_ are already handled. The genuinely absent shapes are github_pat_, ghs_, ghu_, ghr_, Slack xox[bpaso]-, Google AIza…, and Stripe's underscore sk_live_ form.

C5 — Attachment path (this task's brief, not a report defect).

ai-orchestration-preliminary-study-2026-07-29.html does not exist at the repo root; it is docs/ai-orchestration-preliminary-study-2026-07-29.html, the HTML twin of the Markdown study. Three distinct documents, not four.

C6 — Branch provenance disagreement between the two orchestration documents.

The 2026-07-30 review header records branch claude/user-owned-ai-orchestration-qaxol8; the study's own handoff and the harness review both say main. The current checkout is main and the files are present here, so the work landed — but a future agent reading the header alone would look for a branch that is not the one to build on.

9. New findings the reports did not make

These emerged during verification. They are observations about the code, not authorizations to change it.

#ObservationWhy it matters
N1 The permission gate keys off args.path only (permissions.js:194). The whole "target-aware" defence rests on one argument name. Any current or future tool that carries a filesystem target under a different key — or carries a second path — gets no resolveFileTarget check at all. This generalises HE-01 from "some tools have thin execute paths" to "the gate itself has a single-argument shape assumption". Worth a test.
N2 list_files does not call confinePath at all in execute (list-files.js:34 is a bare path.resolve). The review flagged the basename existence leak but not that the directory-confinement for this tool is also gate-only. Same defence-in-depth class as HE-01, one tool further out.
N3 glob.js already uses resolveFileTarget (glob.js:105) as well as confinePath (:131). The review's HE-01 narrative implies only permissions.check adopted the new choicepoint. At least one tool has migrated. Whoever implements HE-01 should treat glob.js as the in-tree reference pattern rather than inventing a new one.
N4 tool-catalog.js:132-152 throws at load time if any tool is in two capability groups or in none. This is a stronger structural invariant than anything the review credits, and it is the reason the capability surface cannot silently drift. It belongs in the future ARCHITECTURE.md.
N5 CLAUDE.md "Known live gaps (as of 2026-07-25)" still describes the symlink deny-matrix gap as observed and unremediated. Same staleness class as the threat-model drift HE-08b flagged, but in the file Claude Code auto-loads. Every Claude session currently starts believing a gap is open that resolveFileTarget substantially closed at the gate. This is arguably higher-impact than the threat-model drift because of the auto-load path.
N6 Scrubbing base64 contentBlocks is not straightforwardly the right fix for HE-08b. A regex scrub over base64 will not match a secret inside an image, and will not match a secret inside a PDF's compressed streams either. The real control is the path gate deciding whether the file may be read at all, plus a size/type policy. Recording this stops a future agent from implementing an expensive no-op.

10. Open questions

  1. Is HE-01 still the right shape after glob.js? If one tool already calls resolveFileTarget in execute, the remaining work may be smaller than the review implies — or the two call sites may have diverged. Needs a call-site-by-call-site diff before anyone writes code.
  2. Which document is the authority on the symlink gap? CLAUDE.md (open), docs/threat-model.md (open), and the harness review (mostly closed at the gate, residual at the tool layer) disagree. The single-tracker rule says the concordance assessment decides — but the concordance tracker was not consulted for this question. Needs Alan or a designated agent to pick one and annotate the others.
  3. Was HE-08b's "no durable chaos-ok marker" ever meant to be closed? It is confirmed true, and it is also listed as Safari S2-05 / F6. Two IDs, one gap, and neither namespace currently owns it.
  4. Does the coordinator path lose safety, not just features? HE-03 frames the dropped kernel options as feature drift. capabilities is on that list, and capabilities determine which tools exist. Whether a coordinator-launched run ends up with a wider or narrower tool surface than the operator intended was not determined here and is the one part of HE-03 with a possible safety edge.
  5. Should the three orchestration documents be treated as load-bearing for runner work at all? Their runner claims are true but thin. Their value is the external landscape, which this validation did not and could not check. Treat their §3 mapping as verified; treat everything else in them as unverified third-party research.
