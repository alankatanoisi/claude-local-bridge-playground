Plain-language summary

The branch does what it set out to do on its main path. When a stop (Ctrl-C, or SIGTERM, the “please stop” signal another program sends) lands while the host is checking the planner’s paid answer, the answer is kept, and --resume re-checks that same answer without paying the planner again. Every tampering case tried was refused before anything was written. The three small fixes (Low #5 exit codes, Low #6 shared file names, Low #7 named torn-line error) are correct, with one gap in Low #5.

Two real problems, one cause. The code decides “was this the model’s fault or the computer’s fault?” by asking “is a stop pending?” and “which catch block am I in?”. With a planner ladder, a disk failure buys an answer from the more expensive model (Medium #1). A program that would normally be rejected, arriving together with a stop, now crashes the run instead of being recorded and stopping cleanly, which main handles correctly today (Medium #2). One small fix (label the model’s mistakes explicitly) closes both.

What the branch buys in practice (measured): for a valid plan, main already keeps the paid answer when you stop during the check, because the check finishes within its 2-second cap. The branch stops sooner, and it also makes “stopped while checking a plan that would have been rejected” resumable, which main refuses.

Findings

Medium1. Ladder runs: a storage failure buys a pricier planner answer

The accepted-plan writes moved out of the validation catch (coordinator.js 635–647) but now throw into the ladder catch (498–512), which escalates on any non-abort error.

Tree Planner calls Final plan model
main cheap:1, cheap:2 (same-tier repair) cheap
branch cheap:1, strong:1 (escalated) strong

The pinning test (planner-resume.test.js 84) uses a one-tier ladder, so it passes falsely for ladders. Reach: opt-in only (run-workflow.js --planner-ladder).

Medium2. A real rejection during a stop now crashes the run

coordinator.js 610–619 rethrows every non-cancellation error raw when a stop is pending, including pre-lint, validation, and evaluator program failures. The comment below it (620–622) still says rejections are recorded during a stop.

Tree Outcome Events
main returns aborted plan_rejected, run_aborted
branch throws the pre-lint message plan_response_received only

No money is lost (resume re-rejects, then pays one legitimate repair). The record and exit code are wrong.

One fix for #1 and #2: mark verdict errors at their source (pre-lint, validator, evaluator ok: false, output ceiling). Only verdicts may record _rejected, feed the repair prompt, or escalate, stop or no stop. Cancellation records _evaluation_interrupted. Everything else rethrows untouched from both catches.

Low3. Low #5 fixed only in the matrix loop

run-workflow.js 69–72 and the --resume path still set exit code 1 after a signal, and this branch makes that path more reachable.

Low4. Unhandled EPIPE when a stop kills the evaluator early

No 'error' listener on the evaluator’s stdin (starlark.js 76–84). Reproduced with a 300 KB payload: run_aborted is written, then the process dies with exit code 1. Latent for today’s payload sizes; a one-line fix.

Low5. New child-process tests write into the real runs/ folder and can hang

run-abort.test.js 47–103 runs the real matrix command, adding 4 folders to starlark-host/runs/ on every suite run (main: 0). Its ready wait never fails on early exit, so a same-millisecond folder-name collision hangs it: 2 of 48 parallel runs here.

Low6. One rule, three copies

The evaluation fingerprint, the recovery policy, and artifact confinement are each built in two or three places. They agree today, and drift fails closed. The receipt’s rejection field is never used and copies rejected source into the event log.

Low7. Docs owed when this lands on main
